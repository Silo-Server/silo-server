# Silo 1.0 release readiness

How the 1.0 release is tracked, validated, and certified. The **product scope of record** is
the published release definition at
[siloserver.org/milestone/1.0](https://siloserver.org/milestone/1.0/). This document does not
restate that scope; it translates it into operational release work. At scope lock, record the
exact `siloserver.org` source commit rather than relying on the mutable published URL. API lock
rules: [../architecture/api-versioning.md](../architecture/api-versioning.md). Scope-lock
status: [../architecture/v1-scope.md](../architecture/v1-scope.md).

Day-to-day sequencing lives on the
[Silo v1 project board](https://github.com/orgs/Silo-Server/projects/5), not here.

## Tracking model: three lanes

The milestone has three separate tracking layers. Do not turn the second or third layer into a
parent for the first:

1. **Feature parents** - one cross-repository parent issue per named feature card in the
   published milestone, currently 35, coordinated in `silo-server`. The parent owns the user
   outcome, surfaces, acceptance criteria, implementation links, and feature-level validation.
   Existing per-platform family issues are implementation children; do not mint duplicates.
   Implementation PRs link the parent but do not close it. The parent closes only after
   implementation, documentation, validation, and acceptance. Create a sub-issue only for work
   that is independently owned, reviewed, scheduled, or blockable; otherwise use a checklist.
2. **Library certification** - three end-to-end certification issues: Movies, Series, and
   Audiobooks. Each proves the complete library experience across iPhone, iPad, Apple TV,
   Android phone, Android tablet, Android TV, and web. Certification exercises many feature
   parents but does not replace them. Each certification records and exercises the applicable
   first-party metadata plugins: TMDB for Movies, TMDB and TVDB for Series, and
   `audiobook-metadata` for Audiobooks. Sports content delivered through the Sportarr metadata
   plugin is not part of the first-party library-certification matrix.
3. **Release-readiness gates** - nine cross-cutting pass/fail conditions below. A feature may
   be deferred and made unreachable; an applicable release gate may not be silently waived.

Existing issues keep their repository, title, and labels. Give each a primary feature parent or
blocker epic for ownership, but also record every additionally affected feature or gate. A
cross-cutting bug must not disappear merely because it has one primary parent. An issue that
violates a core acceptance item or gate is a candidate blocker; the release owner makes and
records the final classification. Deferred capabilities are labeled for a later release and
stay outside the 1.0 execution structure.

## Current blocker epics

The current milestone baseline has nine blocker epics. Their complete acceptance language stays
in the published release definition; the project board owns their implementation issues:

1. remove in-app account creation;
2. implement and validate backup and restore;
3. certify HDR-to-SDR tone mapping on the supported backend matrix;
4. lock the 1.0 scope and record its exact baselines;
5. freeze the `/api/v1` contract, publish its public reference, and reject breaking changes;
6. validate first-run and upgrade from the named supported prerelease baseline;
7. enforce deferred-surface boundaries in release builds;
8. strict-gate ebook and manga surfaces for 1.0; and
9. certify the named Jellyfin and Audiobookshelf compatibility clients and boundaries.

## Validation: two phases

**Phase 1 - rolling feature acceptance.** Validate a feature parent whenever its implementation
is complete. Walk its acceptance criteria, record the complete validated release set described
below, update the [validation ledger](validation-ledger.md), label the issue `validated`, and
close it. This work starts immediately and runs in parallel with remaining blocker work. A
later relevant change explicitly invalidates and reopens the parent.

**Phase 2 - release-candidate certification.** The three library certifications and nine gates
receive their initial complete run against the first immutable release candidate, never against
moving `main`. A later RC carries unaffected evidence forward only through the recorded
RC-to-RC review described below.

All validation uses a **persistent validation library set**, versioned independently from the
application builds. It includes at least one 4K HDR title, one DV7 title, a multi-season series
with specials, a chaptered audiobook, and non-ASCII filenames.

## Validated release set

Feature, certification, and gate evidence must identify every artifact it exercised:

- server tag, commit, and immutable container digest;
- Apple commit, marketing version, build number, and distribution build identity;
- Android commit, version, build number, and distribution artifact identity;
- website commit when the feature or documentation surface applies;
- plugin SDK, catalog, and first-party plugin commits or versions when applicable;
- validation-library snapshot, environment, validator, date, procedure, result, evidence link,
  and known limitations.

Use `not applicable` with a reason rather than leaving an identity blank. A value such as
"latest" is not evidence.

## Regression control

Validation results bind to the release set on which they ran. The
[validation ledger](validation-ledger.md) records one row per validated feature parent, its
cross-repository identities, evidence, and coarse owning path prefixes for each repository.

Two advisory PR checks watch the ledger; neither is a merge gate or a release-owner
disposition:

- `validation-impact-advisory` is the deterministic floor: it compares a server PR with the
  **base branch's** validated ledger and reports server path overlaps. An overlap means
  "review the validation impact," not "revert" and not automatically "revalidate."
- `validation-impact-agent` is the agentic layer: Claude reads the actual diff and ledger and
  reports (a) behavioral impact on validated features that path matching cannot see — shared
  contracts, migrations, capability or serialization changes, with a named mechanism and
  confidence — and (b) features this PR may make **ready for validation**, including
  `revalidate` rows it may resolve. It runs only once the ledger has data rows, skips drafts
  and fork PRs, and posts one sticky comment. Its findings are recommendations only.

Neither check can observe Apple, Android, website, SDK, catalog, or plugin changes; those
repositories need equivalent detectors or a future central check.

The PR template also asks authors to declare behavioral impact that path matching cannot see.
That declaration is input, not proof.

Before RC stabilization, replace or supplement the advisory detector with a required
cross-repository validation-disposition check. It must remain failing until an authorized
reviewer records one of these outcomes with reasoning:

1. no validated capability is affected;
2. prior evidence remains applicable and is carried forward;
3. named feature, certification, or gate evidence is invalidated and must be rerun;
4. required revalidation is complete and linked.

Agentic diff review (including `validation-impact-agent`) may recommend affected IDs, but it
does not make the disposition. A short
universal **smoke suite** also runs on every RC: fresh login, browse each shipping library type,
play one title per type, resume, one download, and one cast.

## Main-line release sequence

Silo 1.0 uses main-line stabilization. Do not create a release branch before RC1.

1. Batch-create the 35 feature parents, three library certifications, nine gates, and nine
   blocker epics. Triage existing open issues into that structure.
2. Complete rolling feature acceptance while release blockers close on `main`.
3. Lock scope and record the exact website, server, and client baseline commits.
4. Freeze `main` for 1.0. Only fixes for core acceptance failures, gates, packaging, or approved
   release blockers merge. New features and unrelated refactors wait.
5. Tag the exact server commit `v1.0.0-rc.1`, build once, and create the immutable RC release
   manifest containing the validated release-set identities.
6. Run the complete three-library certification and all nine gates against RC1.
7. If a fix is required, merge the narrow fix into frozen `main`, tag the next candidate
   (`v1.0.0-rc.2`, and so on), and record the complete RC-to-RC diff and validation disposition.
8. When a candidate is accepted, add `v1.0.0` to the exact certified server commit. Promote the
   already-certified container digest and client artifacts; do not rebuild, move, or delete the
   RC tag.
9. Create `release/1.0` from `v1.0.0` only after release. `main` may then move toward 1.1.

The [release automation](../release-versioning.md) must support semver RC/final tags, creating
the final tag on an already released RC commit, and immutable versioned container aliases before
RC1. The current main-only release rule is compatible with this stabilization model; versioned
artifact publication and promotion remain release implementation work.

For 1.0.x, fixes target `release/1.0` and are forward-ported to `main` before the patch release
unless the release owner records why they do not apply. Patch releases use new tags such as
`v1.0.1`; published tags never move.

## RC-to-RC evidence carry-forward

Every later RC has a release-candidate issue or equivalent immutable record containing:

- the complete new release manifest;
- every commit and PR changed since the prior RC across all included repositories;
- affected feature, library-certification, and gate IDs;
- evidence rerun on the new RC;
- evidence carried forward, with the reviewer and reason it remains applicable;
- the universal smoke-suite result.

Only evidence covered by this review carries forward. This avoids unnecessary full manual
recertification while still producing a defensible evidence set for the final RC.

## Release-readiness gates

Track these as nine gate issues. Gate issues link any implementation blockers and close only after
the release-candidate evidence passes; they are not where missing capabilities get built.

1. **First-run.** A fresh default installation reaches usable - create admin, add a library,
   scan, browse, and play - through documented steps without manual database or configuration
   editing.
2. **PostgreSQL durability.** The default Docker Compose stack provisions PostgreSQL, and a
   documented external PostgreSQL deployment works with operator-supplied credentials and
   connection details. Core state survives application restarts and container replacement.
   Connection and migration failures are visible and block ready status.
3. **Redis coordination.** The default Docker Compose stack provisions Redis, and a documented
   external Redis deployment works. Modes and features that require Redis fail visibly and report
   not ready during an outage; integrated deployments document which functions fall back
   in-process. Restarting Redis may interrupt transient work but does not corrupt durable library,
   user, or playback-history data.
4. **Upgrade, backup, restore, and recovery.** The release owner names one supported prerelease
   baseline, normally the final public beta or release candidate. Its database migrates
   automatically and non-destructively to 1.0, and failure does not leave a partially upgraded
   database. Backup and clean-host restore cover PostgreSQL, object storage, server configuration,
   per-user stores, and the secret-encryption key; Redis remains disposable. "Rollback" means
   restoring the documented pre-upgrade backup unless a separately tested reverse procedure is
   explicitly supported. Historical development builds outside the named baseline have no
   upgrade guarantee.
5. **Security and secret handling.** Provider tokens, SMTP credentials, object-storage keys,
   watch-sync OAuth tokens, and plugin credentials are encrypted at rest, redacted from logs
   and API responses, and survive migration. Stream URLs are expiring and profile-scoped;
   unauthenticated or wrong-profile requests fail; no shared or compiled-in secret grants media
   or remote-control access.
6. **Observability.** Failed scans, transcodes, and metadata matches identify the affected item
   and reason to an administrator. `/health` and `/ready` accurately reflect dependency
   outages.
7. **Compatibility, packaging, and public API reference.** The native API, plugin SDK, and
   migration path publish version and minimum-version policies. Release automation emits semver
   tags and immutable versioned artifacts. Before release, siloserver.org serves the canonical
   versioned `/api/v1` reference at a stable URL, generated from the frozen OpenAPI contract for
   the server tag, with a downloadable contract. CI rejects breaking changes to the locked
   contract. The version-skew matrix covers every 1.0 client against the 1.0 server, the final
   supported prerelease clients against the 1.0 server, and 1.0 clients against the named
   prerelease server baseline. Jellyfin and Audiobookshelf results live in
   [compatibility-validation.md](compatibility-validation.md).
8. **Scope enforcement.** Release builds do not expose deferred functionality: capabilities
   report unsupported, clients have no entry point, public docs do not advertise it, and
   strict-gated routes return the documented unavailable response. Automated release checks
   enforce the boundary.
9. **Public-release compliance.** First-party providers comply with applicable terms and
   production rate limits; bundled credentials are audited. Dates and times honor device locale
   and timezone, and non-ASCII titles and paths scan, browse, and play correctly.

## Bug bar

A bug blocks 1.0 only when it violates a core acceptance item or release gate. Material security,
data-loss, and required-artifact failures must be mapped to the affected acceptance item or gate,
not treated as a separate undocumented blocker class. The release owner records that judgment
and the affected criteria. Other bugs move to 1.0.x.
