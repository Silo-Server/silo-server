# Notification webhook revisions

`notification_webhooks.revision` is a server-owned bigint allocated from a non-cycling PostgreSQL sequence. The insert/update trigger assigns it for every write, including existing bridge configuration updates, signing-secret rotation, delivery success/failure bookkeeping, and disabling a destination. It does not depend on transaction timestamps. Gaps are expected, and a recreated row receives a new revision even if its ID or supplied revision repeats. Sequence exhaustion fails writes rather than reusing a validator.

Apply the migration before deploying binaries that select the revision column. Existing binaries continue to use the same SQL columns and v1 wire responses; their inserts and updates pass through the database trigger. All writers must use the migrated database with the trigger enabled. Trigger bypass, manual sequence reset and independently restored divergent databases are outside this guarantee. This migration does not enroll a user or activate delivery.

The repository's guarded deletion seam locks the profile-owned row, invokes the caller's precondition check on its current revision, and deletes within the same transaction. A mismatch returns without deleting the row or cascading its attempts. Missing and foreign-profile rows report not found. Concurrent writers serialize through the same row lock; an editor that wins first makes the original deletion revision stale. A writer that loses to a committed deletion cannot update that deleted row.

The revision covers operational metadata as well as configuration, so a provider outcome may invalidate an editor's validator. This is conservative lost-update protection, not a configuration-only version. Provider dispatch and retry semantics otherwise remain unchanged, and a database deletion cannot recall an external request already sent. The v2 transport owns validator rendering and conditional-header evaluation; the storage package does not interpret HTTP headers.
