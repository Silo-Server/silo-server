# Native API contract: Huma and `/api/v2`

**Status: accepted for Silo 1.0; implementation pending.** Tracking issue:
[#135](https://github.com/Silo-Server/silo-server/issues/135). Commands assume the repository
root is the cwd.

This document records the contract and release decision for Silo's native API. It is durable
architecture, not an implementation schedule: sequencing and progress belong in issue #135 and
its pull requests.

## Decision

Silo 1.0's first stable native API is `/api/v2`.

The current `/api/v1` surface is an alpha contract. It will be frozen, carried only through a
bounded pre-1.0 bridge, and removed from the 1.0 server except for a retirement tombstone. Silo will
not maintain two native business APIs indefinitely.

The pre-1.0 native HTTP surface is broader than that prefix. The proxy and transcode-node
listeners currently expose native stream, download, media-delivery, and internal-control routes
mostly at version-neutral paths, plus their own `/api/v1/health` routes. In this document,
**legacy native surface** means both the main API router's `/api/v1` namespace and those
alpha-native routes on the other listeners. It excludes Jellyfin and Audiobookshelf compatibility
protocols, plugin RPC, and operational endpoints. The main API listener's tombstone cannot retire
routes on another listener; every proxy/transcode-node route therefore receives its own explicit
move, replacement, retention, or removal disposition.

The v2 JSON API is implemented with Huma v2 mounted on the existing chi router through the
`humachi` adapter. Go input and output types are the source of truth. Huma derives OpenAPI 3.1 and
JSON Schema from those types and applies the same request validation at runtime. The generated
spec is committed under `contracts/api/v2/`, served by the running server, and reproduced in CI.

This is a contract reset, not a mechanical change of path prefix. Every route in the legacy native
surface receives an explicit v2 disposition: carried forward, redesigned, replaced, removed,
compatibility-only, or outside the native JSON contract. Wire changes must be intentional and
reviewed. The existing implementation is evidence about product behavior, not an automatic
compatibility requirement: v2 replaces alpha-era shortcuts and framework accidents with current
HTTP and API best practices. Existing behavior is preserved when it expresses intentional product
semantics, security, or a demonstrated client requirement. Conversely, v2 does not churn an
endpoint merely for aesthetic consistency when no concrete contract problem is being fixed.

## Why v2 instead of converting v1 in place

Silo is still alpha and the server, web client, and first-party native apps can ship a coordinated
transition before 1.0. That is the one inexpensive opportunity to remove accidental shapes and
make Huma's validation behavior part of an intentionally designed contract.

Converting the existing surface in place would require treating every omission rule, inconsistent
status, anonymous response object, and permissive decoder behavior as compatibility-sensitive
while simultaneously changing the transport framework. It would spend most of the migration
budget preserving alpha behavior and then lock that behavior into 1.0.

A permanent v1/v2 split would be worse: self-hosted servers and independently updated clients
create real version skew, and duplicated handlers inevitably drift. The bridge therefore exists
only to sequence releases safely; it is not a support policy.

## Contract architecture

### Source of truth

- Typed Huma operation definitions in Go own native JSON request parameters, request bodies,
  response bodies, headers, statuses, validation constraints, operation IDs, and schema names.
- `contracts/api/v2/openapi.json` is a deterministic generated artifact. It is never edited by
  hand.
- It is the single native OpenAPI artifact. Huma contributes structured operations and a small
  typed manual registry contributes stable raw HTTP handshakes that OpenAPI can describe; Silo
  does not publish separate structured and raw specifications.
- Stable operation IDs and schema names are contract identifiers. After the 1.0 lock, renaming
  either is treated as a breaking change even when the HTTP path and JSON happen to be unchanged.
- The runtime serves the exact committed contract at `/api/v2/openapi.json`. A build whose
  generated bytes differ from the committed artifact fails CI.
- All stable v2 operations are registered when the router is built, regardless of whether an
  optional provider or integration is configured. Capability documents report availability;
  optional dependencies do not make the contract itself nondeterministic.

Huma transport types stay close to the operation that uses them. Business behavior remains in
the package that owns the domain. During the bridge, v1 and v2 handlers call the same application
services; a v2 handler must not proxy to a v1 HTTP handler, and business logic must not be copied
between versions.

Huma validates v2 requests in production. Silo does not schema-validate every response at runtime.
Instead, deterministic fixtures and representative handler responses are validated against the
committed artifact in tests through the real router and middleware, covering serialization,
headers, statuses, and problems. Plain-chi binary, range, redirect, and WebSocket handshakes use
focused protocol tests. No separate runtime response-validation mode is part of the foundation.

Huma and the selected semantic OpenAPI diff tool are pinned to exact versions. An upgrade lands in
its own dependency PR rather than an API-section PR, regenerates the artifact, and runs the
foundation contract snapshots. Generated differences are reviewed explicitly; after the 1.0 lock,
a breaking difference blocks the upgrade. A diff-tool upgrade must still detect a seeded breaking
fixture. Upgrades happen for a needed fix, security update, or useful feature rather than an
artificial calendar, and Huma upgrades are not auto-merged.

The server binary embeds the committed `contracts/api/v2/openapi.json` and serves those exact bytes
at `/api/v2/openapi.json`; it does not regenerate a live document from runtime wiring. The contract
digest in `/api/v2/system/info` is the SHA-256 of those same bytes. CI and local verification
regenerate the artifact from the Go registries and fail on a difference before a release build can
serve it.

The same artifact is published publicly under the project-controlled `siloserver.org` domain.
`https://siloserver.org/api/v2/openapi.json` tracks the current stable v2 release, while
`https://siloserver.org/api/v2/releases/<server-version>/openapi.json` is an immutable release
snapshot. Prereleases publish only their versioned snapshot and do not advance the stable alias.
The release workflow copies the exact committed bytes and verifies their SHA-256 rather than asking
the website to regenerate them. `https://siloserver.org/docs/api/v2/` may provide a browsable UI,
but it is presentation over the raw JSON, not another source of truth. The hosting provider may
change without changing these canonical project URLs.

### Legacy native route inventory

`contracts/api/v2/route-inventory.json` is the enumerated legacy native surface every later
migration decision is measured against: one row per method+path variant (`GET` and `HEAD`, a
WebSocket handshake, and each method of a wildcard `Handle` are separate rows) across four
listeners: the root `http.ServeMux` (`cmd/silo.newRootHandler`), the API router
(`internal/api.NewRouter`), the proxy node and the transcode node (each `(*Server).Handler`). Root
`/api/` rows delegate to the API listener; `totals` and `route_count` are authoritative;
`cmd/route-inventory` generates the file from registration source.

The contract: each listener entry function returns a sealed `http.Handler` — an unexported struct
holding the router in an unexported field, with `ServeHTTP` as its only method — built from an
unexported constructor that the entry function alone calls. The generator checks that shape with
type information, walks the constructor, and enumerates every chi and `http.ServeMux` registration
reachable from it, or fails, as compiled for the linux production build; a build-constrained
non-test file in an audited package is refused. A router-taking helper inside the audited packages
(the four listener packages and `internal/api/handlers`) is followed; one outside them is refused,
as is any router-typed value the walk did not model (closures, immediately invoked functions), any
router produced outside a constructor or a recorded exclusion (Jellyfin and Audiobookshelf compat),
any exported router-returning function in the audited packages, any type assertion, type switch or
generic instantiation whose type is a router by its method set, the `reflect` calls that reach a
method or the memory behind a value (`MethodByName`, `Method`, `NumMethod` on `reflect.Value` or
`reflect.Type`; `reflect.NewAt`; `reflect.Value.UnsafePointer`, `UnsafeAddr`, `Pointer`), an import
of `unsafe` in the audited packages, and `http.DefaultServeMux`. Short of `unsafe`, refused there,
nothing recovers the router; `make lint-router-recovery` reports the same shapes tree-wide in CI.

To add a route: register it inside the constructor or in a `chi.Router`-taking helper it calls in
an audited package, with a literal path and method; run `make route-inventory` and commit the
artifact, which `make verify-route-inventory` byte-compares in CI. As a backstop against a generator
bug, each listener package reconciles a real router at test time through its unexported constructor
(exact for root, proxy, transcode; one-way for API). `deferred_fields` are null; `heuristic_fields`
are evidence, not facts.

### Migration ledger

`contracts/api/v2/migration.json` records the v2 disposition of every row in the route inventory.
Its key is the inventory row's listener, method, exact path, and `registration_index`: the
inventory registers twelve method+path pairs twice, under different middleware or conditions
(for example a rate-limited and an unlimited variant of the same login route), and each
registration is a separate operation with its own consumers and disposition, so the index
disambiguates them in registration order. There is exactly one ledger entry per inventory row and
one row per entry, and the entries follow inventory order.

An entry has two kinds of fields. The first kind is copied from the inventory row — `listener`,
`namespace`, `method`, `path`, `handler`, `handler_kind`, `source_file`, `route_group`,
`middleware_chain`, `auth_class`, `auth_traits`, `conditional`, `conditions`, `delegates_to`
(the inventory's empty string is the ledger's `null`), `request_kind`, `response_media_kind`,
`streams`, and `upgrades_websocket` — plus `profile_required` and `admin_required`, which are
projections of `auth_traits`. `make verify-migration-ledger` (the whole `internal/contractledger`
test package, run in CI) validates the file against `contracts/api/v2/migration.schema.json`,
reconciles every one of those fields against the inventory, reporting drift per field, and
enforces the review rules below. The one permitted override is the ten `dynamic_plugin_proxy`
rows, whose media kinds are recorded as `dynamic_proxy` because a plugin proxy has no static
request or response shape; the override is anchored to the inventory side, so only a row whose
inventory handler is one of the two plugin-proxy literals (`/api/v1/plugin-assets/{installation_id}/*`
and `/api/v1/plugins/{installation_id}/*`) may claim the rule, and any other row that claims it
fails with `dynamic_plugin_proxy rule on a non-proxy handler`. The gate also prints set problems
(missing entry, orphan entry, drift) before the order check and reports only the first order
mismatch, because later ones cascade from it.

The second kind is curated by hand and is what the ledger exists to hold: `consumers` and
`consumer_call_sites` (including `match: manual` and `match: follower` sites), `release_flow`, `tier`, `disposition`,
`disposition_rule`, `disposition_rationale`, `owner`, `review_state`, `v2`, and `notes`. The
schema ties them together: each `disposition_rule` names the document or decision that justifies
it and is therefore allowed only with the disposition it justifies (`maintainer_decision` is the
escape hatch for any); `removed` and `documented_exclusion` rows carry an all-null `v2`; a
`ported`, `redesigned`, or `replaced` row can be `ratified` only with a complete `v2` target; and
every `removed`, `redesigned`, or `replaced` row names an `owner`, which the gate refuses to
ratify while it is a placeholder (anything starting with `pending`, or `tbd`, `todo`, `unknown`,
`none`, compared case-insensitively). Tier is a rule, stated in the file's `description` and
enforced by the gate: tier 1 is the plan's release-critical flows unless the row is `removed`,
since a removed route has no v2 behavior to baseline, so a removed row in tier 1 fails.
`release_flow` is derived from route intent, not path prefix: the acting-admin library
management routes under `/api/v1/libraries/`, the admin scan triggers, and the theme catalog
refresh are `core_admin`, while the viewer-facing `/api/v1/library/{id}/*` reads are
`browse_search`. Proxy and transcode-node rows that are `ported` keep `v2` null by design: those
listeners have no `/api/v2` namespace, so the route is retained at its version-neutral path and
described through the manual registry, never aliased into v2. Because these fields are decisions
rather than derivations, the ledger is gated, not regenerated: CI checks the committed file, and
nothing rewrites it.

Consumer evidence comes from `scripts/apiv2-ledger/`. `extract_consumers.py` scans `web/src`, a
silo-apple tree, and a silo-android tree for HTTP and WebSocket calls, resolving path literals,
helper functions that return a path template, templates rooted at the API base URL, Kotlin
`buildString`/`const val` builders, and Swift `let`/`static let` path bindings;
`match_consumers.py` maps those sites onto inventory rows by normalized path template and method;
`sweep_uncredited.py` then greps the last two static segments of every inventory path across all
three trees and lists every request-shaped hit not already credited, which a maintainer resolves
by hand. Call-site files are repository-root-relative for their repo (web sites are relative to
`web/`), and the schema enforces each repo's root so a mis-rooted site fails the gate. Sibling
sites are pinned: the ledger's `source_trees` header records the silo-apple and silo-android
commit the sites were extracted from (`build_ledger.py` takes both SHAs as arguments), so a
site is re-resolved with `git show <sha>:<file>` against that exact tree rather than a moving
branch. `sweep_uncredited.py`, given the sibling git checkouts, reports a credited file that no
longer exists at the pin as `stale-against-pinned-tree`, separately from an uncredited hit.
`TestSiblingCallSitesResolveAgainstPinnedTrees` goes further for every apple and android site:
the file must exist at the pin, the line must be inside it, and the route's last static path
segment must appear within four lines of the credited line, so a wrong pin whose files still
exist is reported rather than passed. Two site annotations refine that check. A site whose
path is a constant declared elsewhere in the file records `path_literal_line`, the line of the
declaration, and the segment is looked for there instead of at the call line. A site marked
`match: follower` is the validator or resolver that admits a server-supplied URL (the stream
and transcode URLs a client fetches from the playback plan), so it never spells the path and is
exempt from the segment check while its file and line are still verified. The test skips only
when a sibling checkout is absent next to this repository, which is the CI case; a checkout
that is present but has not fetched the pinned commit, or a site that no longer holds up at
the pin, fails it, so `make verify-migration-ledger` cannot print ok over an unfetched pin.
`build_ledger.py` merges a regenerated inventory and consumer map into the committed ledger by
key: it refreshes the copied fields and mechanical call sites (carrying each mechanical site's
`path_literal_line` over by location), preserves every curated field and every manual and
follower site on an existing entry, and seeds defaults only for rows that have no entry yet.
Running it on an unchanged inventory and consumer map rewrites the file byte for byte.
Server-internal and compat consumers (Go URL builders in this repository) are recorded as
manual sites. Absence of a first-party consumer is not proof of disuse; removal needs an
affirmative product decision.

### Contract foundation

The first implementation slice establishes and tests rules shared by every later operation:

- one RFC 9457 Problem Details envelope with stable type URIs, safe human-readable text,
  optional field-level validation details, and request correlation;
- a deliberate distinction between malformed JSON, validation failure, authentication failure,
  authorization failure, missing resources, conflict, rate limiting, and unavailable capability;
- consistent treatment of absent versus `null`, empty collections, timestamps, durations, opaque
  identifiers, booleans, and extensible enums;
- explicit request-body size limits, pagination/filter/sort syntax, idempotency behavior, cache
  validators, and response headers where the operation needs them;
- strict request validation, including unknown properties, unless an operation documents an
  extensibility bag; clients use capability detection before sending optional behavior to an
  older server;
- response models that first-party clients decode leniently: clients ignore unknown response
  fields and preserve an unknown-enum fallback;
- auth, profile, acting-admin, rate-limit, demo-mode, and request-ID middleware behavior identical
  in strength to the existing router.

The exact shared schemas and status mapping land in the foundation pull request before domain
operations begin. Huma defaults are not accepted implicitly: generated validation errors, schema
hooks, requiredness, and unknown-property handling are configured and locked by tests.

The foundation configures the framework rather than inheriting convenience defaults:

- set `RejectUnknownQueryParameters` so undeclared query parameters fail with the validation
  problem instead of being ignored;
- set `NoFormatFallback` so an unacceptable `Accept` header returns `406` instead of silently
  falling back to JSON;
- add a structured-body media-type guard because Huma otherwise treats a missing `Content-Type`
  as JSON and accepts `+json` formats; missing, parameter-incompatible, and vendor media types use
  Silo's `415` problem exactly as specified below;
- disable Huma's default array nullability and require response builders to initialize slices and
  maps, with schema-validated response tests proving that collections never serialize as `null`;
- use a named v2 instant transport type or canonical mapper; ordinary `time.Time` marshaling does
  not guarantee UTC or exactly millisecond precision. Schema and exact-wire tests cover UTC,
  three fractional digits, omission, explicit null where allowed, and zero-value rejection;
- require explicit Huma `explode` metadata for slice query parameters and lint/test every array
  parameter so the accepted repeated-key wire form is not replaced by comma-separated values;
- disable the built-in OpenAPI, documentation, and schema routes and remove the default schema-link
  response transformer; Silo serves the exact committed artifact and omits production `$schema`
  additions as specified above; and
- choose and document an explicit structured-body read timeout before the foundation PR merges.
  The audited Huma default is five seconds and can supersede the server's current 30-second read
  timeout, so it is not adopted accidentally. The chosen deadline, timeout boundary, and Silo
  `408` Problem Details response receive integration tests.

### Problem Details

Every v2 error uses RFC 9457 Problem Details and `application/problem+json`. Silo requires these
members even where RFC 9457 makes them optional:

- `type`: a stable HTTPS URI under a permanent project-controlled documentation origin; its final
  path segment is the machine-readable problem identifier;
- `title`: a short summary fixed for the problem type;
- `status`: the HTTP status code, equal to the actual response status;
- `detail`: a safe occurrence-specific explanation that clients never parse for control flow;
- `instance`: `urn:silo:request:<request-id>`, matching the `X-Request-ID` response header.

Validation failures add an `errors` array. Each entry contains `location` using the documented
`body.*`, `query.*`, `path.*`, or `header.*` grammar, a stable `code`, and a safe `detail`.
Rejected values are never echoed. Stack traces, database/upstream errors, filesystem paths,
internal node URLs, credentials, tokens, private media data, and other implementation detail are
never returned to the client. Problem responses default to `Cache-Control: no-store` unless a
specific public problem is reviewed as cacheable.

Server logs remain useful to the self-hosting administrator. They use the existing structured
logger and `logredact` key-based secret filtering rather than a v2-specific redaction framework.
Authorization fields, cookies, passwords, API keys, tokens, and secret URL or query values are
never logged; request and response bodies are not logged by default. Code keeps secrets out of
free-form messages and sanitizes upstream errors or URLs before logging when they might embed a
credential. Non-secret media names, filesystem paths, and internal hostnames may appear in local
logs when they are operationally useful. Hosted diagnostic bundles retain their separately owned
sanitization policy.

`logredact` filters by structured key and does not inspect arbitrary values. The foundation work
therefore audits URL and free-form log fields, removes or sanitizes any credential-bearing value,
and adds regression tests for those call sites; existing key-based filtering is not treated as
proof that every current message is safe.

The initial shared type catalog includes malformed request, validation failure, authentication
required, invalid token, session expired, permission denied, resource not found, method not
allowed, resource conflict, idempotency conflict, payload too large, unsupported media type, rate
limit exceeded, capability disabled, dependency unavailable, client upgrade required, and
internal error. Domain-specific types are added only when a client needs distinct corrective
behavior.

The foundation adapter replaces Huma's default problem output where necessary: every response has
a Silo type and instance; validation details add stable codes and omit Huma's rejected `value`;
the production body omits Huma's optional `$schema` member. Malformed syntax uses `400`,
authentication `401`, authorization `403` (or hidden `404`), missing resources `404`, state or
idempotency conflicts `409`, unacceptable representation `406`, configured request-body timeout
`408`, oversized bodies `413`, unsupported media `415`, typed/domain input validation `422`, rate
limiting `429`, unexpected failures `500`, and temporary dependency unavailability `503`.
`Retry-After` accompanies `429` and applicable `503` responses.

### Success responses

An individual resource is a bare typed object; v2 does not add a universal `data`, `result`,
`response`, or `success` wrapper. A missing individual resource returns a Problem Details `404`,
not `200` with `null`.

Collections use an object envelope with a required `items` array. Empty collections are
`{"items":[]}`; `items` is never null or omitted. Paginated collections add a `page` object with
the agreed cursor state. Bounded unpaginated collections may omit `page`. Exact or estimated
totals are added only for a concrete consumer when their cost is acceptable; the envelope may
carry other typed collection-wide metadata.

Resource creation returns `201 Created`, a `Location` header, and the canonical created
representation. Replacement or patch returns `200` with the canonical updated representation.
Deletion returns `204 No Content`. A synchronous command returns `200` with a typed result when
it has one and otherwise `204`; accepted asynchronous work returns `202` with a typed job resource
and `Location`. A `204` response has no body—not `{}`, `null`, or a success message. Bulk partial
success uses an explicit typed result rather than weakening these rules.

### Wire data representation

Required response fields are always present. Optional response fields are omitted when unknown,
not requested, or not applicable. `null` is used only for a documented “known to have no value”
state that differs from omission. Arrays and maps are never null. Empty strings are values, not
null substitutes. PATCH inputs distinguish omitted (unchanged), explicit null (clear, only when
nullable), and a concrete value through presence-aware transport types; Go pointers and
`omitempty` do not choose the contract accidentally.

Every v2 identifier is an opaque JSON string, including an internal numeric database key that
must cross the wire. Clients do not parse, order, or perform arithmetic on identifiers. Existing
deterministic content IDs keep their established format; new type prefixes are permitted but are
not a global requirement. Path parameters use specific names such as `{library_id}` where a
generic `{id}` would be ambiguous.

Instants are RFC 3339 UTC strings with `Z` and millisecond precision. Date-only values use
`YYYY-MM-DD`. Durations are numeric with the unit in the field name—normally integer
milliseconds for client timing and seconds for coarse expiry—unless an existing normative
protocol such as playback v3 specifies otherwise. User time zones are separate IANA identifiers.

Enums are lowercase strings, never numbers. Request enums are closed and reject unknown values
with `422`; response enums are additive and clients retain an unknown/raw fallback. Existing
values are never renamed or repurposed. Polymorphic objects use a required string discriminator
and named schemas. Request variants are closed; response variants are additive and native clients
retain an unknown-variant representation. Untyped maps are limited to intentional named extension
bags.

### Query and pagination conventions

Query names use snake case. Array values use repeated parameters; comma-separated arrays are not
accepted except inside the separately defined `sort` grammar. A scalar repeated more than once is
malformed. Booleans accept only lowercase `true` or `false`. Empty is a value only for parameters
that explicitly permit an empty string; it is not null or omission. Invalid percent encoding is
malformed. API paths have no trailing slash and are not redirected to add or remove one.

Filters are declared per operation; v2 has no generic expression language. Sorting uses
`sort=field,-other_field`, an operation-specific allowlist, documented collation/null semantics,
and a server-added unique tiebreaker when needed. Unknown filter or sort fields receive `422`.

Potentially large or mutable collections use `limit` plus an opaque `cursor`, returning the
accepted `page.next_cursor` and `page.has_more` fields. The default limit is 50 and the global
maximum is 200; an operation may set a lower maximum. Cursors are URL-safe, tamper-resistant, and
bound to the operation, security scope, filters, effective sort, and unique tiebreaker. Clients do
not decode or construct them. Malformed, tampered, or context-mismatched cursors receive `400`
with the invalid-cursor problem type. Cursors contain no credentials or sensitive metadata in
reversibly encoded unsigned form.

Small naturally bounded collections return only `items`. Generic offset/page-number pagination
is not part of stable v2; a specialized administrative/reporting exception requires its own
section review. Exact totals remain opt-in when a real consumer justifies their cost.

### HTTP representation and lifecycle conventions

Successful structured responses use `application/json`; errors use `application/problem+json`.
JSON request bodies require `Content-Type: application/json`; `charset=utf-8` is the only tolerated
parameter. Unsupported media types, charsets, and vendor `+json` types return the unsupported-media
problem. JSON is UTF-8 and response content types omit the redundant charset parameter. A missing
`Accept` field or `*/*` accepts the operation's representation; a request that accepts none of an
operation's documented representations receives `406 Not Acceptable`.

Response compression is negotiated through `Accept-Encoding` and emits the applicable `Vary`
field. Compressed request bodies are rejected by default; supporting one requires an explicit
operation contract, decoded-size enforcement, and decompression-bomb tests. `HEAD` exists only for
an explicitly registered and documented operation. When registered, it has the corresponding
`GET` status and headers without a response body; it is not enabled automatically for every read.

Structured JSON request bodies have a default maximum size of 1 MiB, enforced before full
allocation or decoding. An operation may lower this limit. Raising it requires an explicit limit,
rationale, and boundary tests in that operation's contract ledger. Large payloads use a designed
multipart or streaming operation rather than a large JSON document. Multipart operations declare
both total and per-part limits and enforce them while streaming, before storage is finalized or
domain behavior runs. Exceeding any body limit returns the payload-too-large problem.

The server generates an opaque canonical request ID for every request, returns it in
`X-Request-ID`, and uses the same value in a problem's `instance`. An arbitrary client-supplied
value never becomes the canonical ID. `Retry-After` uses delta-seconds on `429` and applicable
`503` responses. V2 does not define legacy `X-RateLimit-*` fields or freeze a pre-RFC rate-limit
draft; standardized fields may be added after the IETF specification is final.

An operation deprecation uses the RFC 9745 structured date form
`Deprecation: @<unix-seconds>` and links to migration documentation with
`Link: <...>; rel="deprecation"`. `Sunset` is sent only when an actual removal date is planned,
uses the RFC 8594 HTTP-date form, and never precedes the deprecation date. Field-level deprecation
that cannot be conveyed by a response field is recorded in OpenAPI and migration documentation.
Every applicable representation, body limit, and response field is explicit in the operation
contract or ledger; a Huma upgrade must not silently change these behaviors.

### Operation and schema ownership

Operation IDs are explicit, globally unique, lower camel case, and action-first, such as
`listLibraries`, `getLibrary`, `createLibrary`, `startLibraryScan`, and `getSystemInfo`. They name
product behavior, never handlers, database tables, frameworks, Go packages, or the API major.
Schema component names are explicit PascalCase product names such as `Library`, `LibrarySummary`,
`CreateLibraryRequest`, `LibraryCollection`, `PageInfo`, and `Problem`. Huma-generated generic
names, Go implementation artifacts, and anonymous top-level JSON objects do not enter the
committed contract. Every top-level request, success response, problem extension, event, and job
object has a stable name; primitive parameters may remain inline.

Each operation has exactly one primary lowercase domain tag, such as `libraries`, `playback`,
`auth`, `plugins`, or `system`. The tag identifies the API section and owning pull request. Paths
use lowercase plural resources and hyphenated multiword segments; path parameters are specific
snake-case names. Commands are modeled as resources when a durable resource or job exists, rather
than accumulating RPC-style action paths. An explicit command operation remains valid when no
meaningful resource exists.

Operations share a component only when its meaning, authorization visibility, requiredness,
nullability, and expected evolution are the same. Purpose-specific projections such as
`MediaItemSummary` and `MediaItem` are preferred over one universal object filled with optional
fields. Each shared component has one owning API section in the contract ledger. Foundation owns
the genuinely cross-cutting problem, validation, pagination, and job components. A pull request
that changes a shared component lists every affected operation, fixture, and first-party client
model and is reviewed as cross-section scope. Free-form maps exist only as named extension bags
with documented trust and size boundaries.

### Credential continuity

Credentials belong to the Silo server, not an API major. Existing login sessions, access and
refresh tokens, profile-lock state, and API keys remain valid through the bridge and 1.0 cutover
until their normal expiry or revocation. V1 and v2 share one session/revocation model during the
bridge; v2 does not mint a parallel credential universe. `Authorization`, `X-Profile-Id`, and
`X-Profile-Token` retain their security meanings, as do account/profile, primary-profile,
acting-admin, server-admin, and hidden-resource checks.

The short-lived plugin access cookie is transport-specific because its current path is
`/api/v1`. V2 plugin launch issues the same five-minute, `HttpOnly`, `SameSite=Lax` credential on
a narrow common v2 plugin-content parent path, using `Secure` on HTTPS. The old-path cookie is
expired on the applicable launch/logout transition where practical and otherwise dies within its
existing five-minute maximum. It is never broadened to `/`.

### Discovery and capability detection

`GET /api/v2/system/info` is always registered, unauthenticated, and usable before login or
profile selection. It exposes at least the server build version, API major, contract digest, and
links to capability documents. The response is bounded — a small fixed document with no
per-request, per-account, or deployment-topology detail — and carries an explicit reviewed cache
policy rather than silently inheriting the structured default. The exact response schema, its
bound, and its cache directives are part of the foundation contract.

Exposing the server build version and contract digest before authentication is a deliberate,
reviewed decision. An updated client must be able to tell a v2 server from a v1-only alpha server
before it holds a credential, and version obscurity is not a control Silo relies on. That trade is
accepted for these fields only; the endpoint carries nothing else an unauthenticated caller should
not see.

Clients use capability documents to decide whether a feature exists. The server version and
contract digest are for diagnostics, support, cache identity, and last-resort compatibility
messages; they are not substitutes for feature detection.

Every stable operation remains registered regardless of runtime provider wiring. Route presence
means that the operation belongs to the stable contract, not that the current server is configured,
authorized, and healthy enough to perform it. Each optional domain exposes a typed capability
document with an opaque `revision`, a required `state`, an effective `allowed` value when the
document is account/profile scoped, and named domain-specific fields. The common states are
`available`, `disabled`, `not_configured`, and `unsupported`. Response-state additions are
additive; a client treats an unknown state as unavailable. Domain fields are typed rather than
placed in a generic `features` map.

Capability state describes support and configuration, not rapidly changing health or capacity.
An administrator-disabled feature returns the `409 capability_disabled` problem; missing required
configuration returns `409 capability_not_configured`; a server build that fundamentally cannot
provide the behavior returns `501 capability_unsupported`; a visible permission denial returns
`403`; and a hidden resource or feature returns the standard `404`. Temporary dependency and
capacity failures return distinct `503` problems with `Retry-After` when applicable. Schema or
closed-enum input errors remain `422`. Route absence is never used as provider state.

Disabled, unconfigured, unsupported, and unauthorized mutations reject immediately rather than
queueing until configuration changes. An asynchronous operation may durably wait through temporary
capacity loss only when its job contract explicitly promises that behavior. Capability discovery
never grants authority: the operation repeats authorization and current-state checks.

Account/profile capability documents will use `Cache-Control: private, no-cache`, an `ETag` derived
from the exact authorized representation, and conditional `If-None-Match` requests. A capability
change publishes a best-effort, authorization-filtered invalidation event containing only a domain
scope such as `downloads`, `playback`, or `all`; the event never duplicates capability values.
Clients refetch the REST document after an applicable event and also after login, profile changes,
app foregrounding, and before important feature-specific UI. Server-wide changes invalidate all
affected principals; account/profile changes are targeted and never disclose another user's state.

### Mutation retry safety

V2 does not impose a global mandatory `Idempotency-Key` mechanism. Every durable-effect mutation
records its duplicate-submission and connection-loss behavior in the endpoint ledger and selects
the smallest mechanism that supplies a real guarantee:

- naturally idempotent `PUT` or `DELETE` semantics that converge on one resource state;
- a natural key or client-supplied resource identity enforced by a database uniqueness constraint;
- a durable domain operation identity such as a playback attempt, upload, job, or webhook delivery
  ID;
- command coalescing that returns the already-active scan, refresh, sync, or similar job;
- durable state-gated or transactional-outbox dispatch for email, webhook, provider, filesystem,
  and other external side effects;
- a generic idempotency key only when the operation inventory proves that none of the preceding
  strategies fits and the complete scope, fingerprint, concurrency, retention, and replay contract
  is justified; or
- an exceptional, explicitly documented non-retryable operation that clients never retry
  automatically after an uncertain response.

The retry mechanism is cluster-safe and enforced by shared durable state rather than process-local
memory. Concurrent duplicate creation is serialized by the owning database constraint or domain
record; a retry either performs the uncommitted operation or resolves to the existing resource/job.
Long-lived domain IDs take precedence over a duplicate generic mechanism. External effects are
never fired directly from a request in a way that can escape the mutation's durable state and be
duplicated after a lost response.

An `Idempotency-Key` request field appears in OpenAPI only for an operation that implements and
documents its semantics. Silo never advertises or validates the field while silently ignoring it.
Adding supported idempotency to an operation later is additive. Before foundation implementation,
the v1 inventory classifies every durable-effect operation by the strategies above and identifies
any residual group that can justify one shared implementation.

### Optimistic concurrency

Concurrency protection is opt-in per operation rather than a default for every mutation. The
endpoint ledger marks resources with demonstrated lost-update risk, initially including access
groups and policy documents; server, plugin, provider, webhook, and library configuration;
collection definitions and ordering; and destructive administrative deletes whose confirmation
can become stale. Progress, playback, presence, notification-read state, idempotent membership,
jobs, append-only events, and operations with stronger sequence/attempt semantics retain their
domain-specific merge or conflict behavior.

A protected resource has a Postgres row version incremented by every change that affects its
canonical editable representation. The server renders that version as an opaque, quoted, strong
`ETag`; clients never parse its apparent format. Protected editor representations are canonical
for the authorized caller rather than sharing one validator across differently redacted or
localized representations. The storage write atomically compares the expected version and updates
the row, so Postgres remains the concurrency arbiter across replicas without a distributed lock.

Protected `PUT`, `PATCH`, and destructive `DELETE` operations require `If-Match`. An exact current
tag performs the guarded mutation. `If-Match: *` is an explicit overwrite request for an authorized
caller and is not sent automatically by first-party clients. A missing field returns the
`428 precondition_required` problem. A stale tag returns `412 precondition_failed`, makes no
change, and includes the current ETag when the caller remains authorized to see it. A resource that
is missing or intentionally hidden returns `404` before precondition evaluation; a request that
passes its precondition but conflicts with current domain state returns `409`.

Successful protected reads and mutations return the current ETag, and first-party clients handle
`412` by fetching the canonical representation and offering reload, comparison, or a deliberate
overwrite. `If-None-Match: *` supports create-only semantics for client-selected resource IDs.
Conditional reads may return `304`. V2 does not add a generic response-body revision; a body
revision exists only for a domain requirement such as capability invalidation or future offline
synchronization. The implementation follows RFC 9110 parsing and precedence, including lists,
optional whitespace, wildcard rules, and strong comparison, independent of Huma helper behavior.

### Long-running work and cancellation

An operation whose durable target resource is created immediately returns that resource with its
own lifecycle rather than creating a redundant job. For example, a queued download can be a
`201 Created` download whose state advances after creation. A separate job resource is used when
the work is an action, affects multiple resources, produces a report, or has no natural target,
such as a scan, import, export, metadata refresh, or maintenance operation.

Separate jobs live under their owning domain. The initiating operation returns `202 Accepted`, an
origin-relative canonical job `Location`, a polling `Retry-After`, and the canonical job body only
after the job and its work intent are durably committed. Persistence or enqueue failure returns a
synchronous problem instead. A job-based operation always returns the job shape even when work
finishes unusually quickly.

The shared job representation has an opaque string ID, stable `kind`, `state`, `terminal`, creation
time, optional start/finish times, `cancelable`, optional honest progress, and a typed terminal
result/link or safe typed failure. Common states are `queued`, `running`, `canceling`, `succeeded`,
`failed`, and `canceled`. Clients use `terminal` instead of inferring completion from an exhaustive
state list. Progress exists only with a meaningful numerator, denominator, and unit; Silo does not
manufacture percentages for indeterminate work.

Polling the job returns `200`, supports ETag/`If-None-Match`, and includes `Retry-After` while
nonterminal. It remains authoritative; a WebSocket event may invalidate cached state but is never
the only completion signal. A successful job returns a small named result or a link to its
canonical result resource, never an untyped map. A failed job returns a named `JobFailure` with
stable machine identity, fixed title, safe detail, and retryability guidance; the successful job
poll itself remains HTTP `200`. Terminal jobs are immutable except for retention cleanup.

A cancelable job exposes an explicit `POST .../{job_id}/cancel` command. Accepted cancellation
returns `202` with the canonical `canceling` job; repeated pending cancellation coalesces to the
same job; an already canceled job returns `200`; and an already succeeded or failed job returns the
`409 job_not_cancelable` problem. Cancellation is best-effort and does not imply rollback. The
owning operation documents whether partial effects remain, are compensated, or are transactional.
Hidden jobs return `404`.

Jobs remain retrievable for at least 24 hours after reaching a terminal state; a domain may retain
them longer for history or audit. After documented cleanup they may return `404`, so durable result
resources—not job monitors—are permanent references. Retrying failed work creates or coalesces a
new job under the operation's accepted retry strategy; a terminal job is never reset to `queued`.

### Bulk operations and partial results

Every bulk operation has one fixed contract: either atomic or per-item. An operation does not
accept a generic mode flag that changes between those semantics; if a domain genuinely requires
both behaviors, it exposes separately named operations so authorization, retry, and result rules
remain unambiguous.

An atomic bulk operation authorizes and validates the envelope and every item before effects,
then commits all changes in one transaction or makes no changes. Failure returns one RFC 9457
problem for the request, with indexed validation details where useful; it never reports partial
success. Work involving external effects uses a durable outbox or job when those effects cannot be
truthfully included in the transaction. Synchronous atomic success returns a named `200` result or
a bodyless `204`; asynchronous atomic work returns its accepted job with `202`.

A per-item operation rejects a malformed envelope, invalid authentication, unavailable global
capability, failed request-wide precondition, duplicate target, duplicate `client_ref`, or other
structurally ambiguous input before processing any item. After the envelope is accepted, each item
is independently authorized, validated, and committed. A synchronously completed batch returns
`200` with a named result even when some items failed. An asynchronous batch returns `202` with a
job whose terminal result is the same named batch result or a link to it. V2 does not use `207
Multi-Status`; that status belongs to the WebDAV XML `multistatus` contract rather than Silo's
native JSON semantics.

The per-item result contains a required `items` array in request order and an exact `summary` with
`total`, `succeeded`, and `failed` counts. Each item has a zero-based `index`, echoes an optional
bounded request `client_ref`, and is a discriminated named success or failure variant. A failed
variant contains a named `BulkItemFailure` with a stable type, fixed title, corresponding HTTP
status code, safe detail, and field validation details when applicable. It is embedded failure
data, not a standalone Problem Details response. Hidden resources remain item-level `404`s.
Execution order is unspecified unless the operation explicitly promises otherwise.

The shared default limit is 100 items and an operation may lower it. A higher limit requires an
explicit asynchronous design, rationale, and boundary tests; the normal JSON body cap still
applies. Atomic edits to a protected collection use its top-level ETag and `If-Match`. A per-item
operation that edits independently protected resources carries an opaque `expected_etag` on each
item and reports a stale item as `412` without changing it. Each bulk operation also records its
retry strategy. Clients never blindly replay an unprotected per-item batch after losing the
response; nontrivial or external-effect batches use durable jobs so partial progress and results
remain recoverable.

### Response caching

Structured Huma v2 responses default to `Cache-Control: no-store`. An operation may explicitly
override that default when its section review identifies a concrete caching benefit. Capability
documents are the ratified `private, no-cache` exception with an ETag; other reads add validators or freshness
only when their owning section requires them. Authenticated or user-specific data is never marked
publicly cacheable.

Authentication and authorization run before any conditional response is evaluated, so a `304`
never bypasses current access checks. Validators are deterministic across replicas and represent
the authorized response or durable resource version rather than process-local state.

This default applies to the structured Huma surface, not to every response emitted by Silo. Raw
media, ranges, downloads, thumbnails, frontend assets, `Vary`, and TTL behavior remain explicit
endpoint concerns. Their existing deliberate policies are preserved or redesigned with the
owning section instead of being flattened by foundation middleware.

### Browser origins

The native `/api/v2` JSON surface has no global CORS middleware. Silo's bundled web application
and plugin pages use the server's own origin, while Apple, Android, and other native clients are
not governed by browser CORS. The narrow plugin launch cookie remains same-origin and path-scoped;
it does not authorize cross-origin API access.

Media proxy routes retain their explicit cross-origin behavior because a browser player can fetch
streams from a separate proxy or transcode-node origin. Those routes still perform their normal
token or bearer authorization and do not enable credentialed wildcard CORS; CORS is never an
authorization mechanism. Jellyfin compatibility and other non-native surfaces retain their own
tested policies. Support for a separately hosted browser client may later add an explicit
administrator-configured origin allowlist without changing the default native contract.

### What Huma covers

Every native operation whose request and response are structured HTTP data is Huma-typed,
including JSON operations that happen to initiate or describe playback, downloads, tasks, or
plugins.

The following stay on plain chi where Huma adds no runtime value, but a small owning manual
registry adds their stable handshake, headers, statuses, and media types to the same OpenAPI
artifact where OpenAPI can describe them:

- byte streams, ranges, HLS playlists and segments, images, subtitles, archives, downloads, and
  other file responses;
- redirects and public HTML/CSS or asset responses;
- WebSocket upgrade endpoints, linked to the separately versioned message protocol;
- dynamic plugin HTTP proxy paths, which are an explicit documented exclusion because they cannot
  have a finite static response schema.

Each exclusion is named in the migration inventory. “Plain chi” is not permission for an
undocumented JSON endpoint.

The 1.0 cutover deliberately preserves no URL alias from the legacy native surface. The main API
listener's `/api/v1` namespace and descendants are replaced by a `410 Gone` tombstone carrying
the stable `client_upgrade_required` problem code, `Cache-Control: no-store`, and a migration-guide
link. `426 Upgrade Required` is not used: RFC 9110 reserves it for an HTTP protocol upgrade and
requires an `Upgrade` header, while this is permanent retirement of an application route.
Separately, proxy and transcode-node routes—including mostly version-neutral stream, download,
media-delivery, and internal-control paths plus their current `/api/v1/health` routes—move or are
retired according to the ledger; the main API tombstone cannot catch them, and they are not
promised a common failure status. Webhooks, OAuth/browser callbacks, tokenized email links,
media-session URLs, download-manifest assets, and dynamic plugin URLs move to their v2 forms
without legacy aliases. Active playback, background downloads, cached plugin resources,
previously sent email links, and externally configured integrations may therefore need to be
restarted, regenerated, or reconfigured after the upgrade. Silo is alpha, and 1.0 is expected to
be a coordinated or fresh deployment; accepting that bounded break keeps the stable contract and
routers honest.

Operational liveness and readiness are not native-client operations. Silo 1.0 exposes them at
the version-neutral root paths `/health` and `/ready`; they remain in administrator documentation
rather than the native OpenAPI artifact or generated clients. Existing unauthenticated root
`/metrics` endpoints on the API, proxy, and transcode-node servers remain operator-facing
telemetry outside the native client contract. They have no endpoint authentication, so deployments
must restrict their exposure through proxy/network policy where required. They are inventoried so
the cutover cannot remove them accidentally. The administrator
upgrade guide must name every external integration and persisted URL class affected by the hard
cutover, explain how to regenerate it, and provide a post-upgrade verification checklist. The
server must not redirect old URLs containing tokens or secrets.

Jellyfin compatibility and Audiobookshelf compatibility remain entirely outside this contract.
They implement other projects' wire protocols. Playback v3's normative JSON Schemas and domain
semantics remain authoritative for v2 playback payloads. The existing HTTP conformance matrix,
including its legacy/draft-body `426` case, remains a bridge/v1-adapter test; v2 gets a separate
transport matrix and uses the ratified v2 status model (`422` for a protocol-version/input-schema
failure) rather than copying that nonstandard status. The compatibility implementations currently
generate or consume native proxy, transcode-node, stream, and host-plugin URLs. Those internal URL
builders and consumers are migration-ledger rows and must be updated and regression-tested when
the native routes move.

### Contract fixtures

Every committed v2 fixture is treated as public. Fixtures come from deterministic synthetic
builders, never a live server, database export, diagnostic report, or production response capture.
They use fictional identities, media, IDs, credentials, and tokens; relative URLs where allowed;
and reserved origins such as `https://silo.example.test` when an absolute URL is required. They do
not contain real filesystem paths, hostnames, IP addresses, account data, library contents, signed
URLs, or secrets. CI applies the existing local-path check plus a bounded fixture secret/path scan,
and the owning section PR reviews the generated examples without a separate privacy process.

## Client contract adoption

### Web

`openapi-typescript` generates the web contract types from the committed spec. The handwritten
mirror in `web/src/api/types.ts` is retired as each consumer moves to the generated surface. A
typed request wrapper binds method, path, parameters, body, and response together so generated
types do not remain unchecked assertions at call sites.

### Apple and Android

Apple and Android keep handwritten, lenient models. Their UI layers currently consume those
models directly, and generated strict DTOs would make forward-compatible server additions more
fragile rather than less.

The server publishes deterministic per-domain request and response fixtures plus the OpenAPI
artifact. Each native client uses a small sync script to vendor only the fixtures it consumes and
writes a one-line `SOURCE` file containing the exact server commit SHA. Client CI decodes those
fixtures with production models, exercises unknown-field and unknown-enum tolerance, and verifies
the fields the client consumes. Client builds never fetch a live spec from the network, and the
native repositories do not vendor the full OpenAPI document they do not generate code from.

Updated native apps require v2. They use `/api/v2/system/info` to confirm the server contract and
show a clear server-update requirement when connected to a v1-only alpha server; they never
contain a v1 transport fallback or replay a failed v2 request against v1. The bridge supports old
and new client generations independently: old clients use v1 and updated clients use v2. The web
app is bundled with the server and uses v2 only.

Cross-repository coordination stays lightweight. A server section PR may merge independently
during the additive bridge. Issue #135 links a companion Apple or Android PR when that client
consumes the section and otherwise records `n/a`; ordinary server CI never checks out client
repositories. The structured migration inventory continues to prove route disposition and
consumer ownership, but it is not a cross-repository state machine.

For the one-time 1.0 gate, the project freezes one server release commit, resynchronizes both
native clients to that exact SHA, and requires their offline conformance suites to pass. The release
checklist verifies every section's linked PR or `n/a`, the exact client commits/builds selected for
distribution, and that the final server tag resolves to the frozen commit. There is no second
per-client contract digest, separate OpenAPI-delta artifact, or standalone release manifest; the
server commit, `SOURCE` pins, linked PR checklist, and green client builds are the proof.

### Third-party clients

Before 1.0, the project publishes the v2 OpenAPI document, the v1-to-v2 operation mapping, a
migration guide, and the bridge/retirement dates. The alpha v1 contract does not receive a
post-1.0 deprecation window, but its removal must not be a surprise.

## v1 lifecycle and release sequence

1. Freeze v1 feature development. Critical fixes needed to keep the bridge usable may still land;
   new stable contract work targets v2.
2. Ship one pre-1.0 bridge server with the complete legacy native surface and v2 routing. The
   bridge keeps old clients usable while v2 clients and the contract gates are exercised.
3. Ship Apple and Android builds that require v2 and clearly require a server update when
   connected to an older v1-only alpha server. Ship the web client on v2 in the bridge server.
4. Verify the release matrix and observe v2 operation/error metrics through the bridge window.
5. Ship Silo 1.0 with the legacy native route registrations removed or moved to their accepted v2
   forms. On the main API listener, explicit retirement handlers cover `/api/v1`, `/api/v1/`, and every descendant and
   return `410 Gone` with the existing v1-shaped `client_upgrade_required` error, pointing the
   user toward a v2-capable client and the administrator upgrade guide. They contain no business
   behavior. Version-neutral legacy routes are retired individually and are not aliases into v2.
   Root `/health`, `/ready`, and operator `/metrics` remain outside the handlers.
6. Remove bridge-only legacy transport code after the 1.0 cutover is established; no updated
   client contains a legacy native transport path to clean up.

Extending coexistence beyond one published bridge release requires an explicit architecture
decision with an owner and removal date.

### Cluster cutover policy

The alpha-to-1.0 update is a maintenance-window operation, not a zero-downtime rolling-upgrade
contract. Administrators drain or stop active work, take every API replica and remote
playback/transcode node out of service, deploy the matching 1.0 components, and then return the
homogeneous deployment to service. Active playback and transfers may need to restart.

Silo does not support a fleet that mixes v1-only alpha API replicas or workers with 1.0
components. API-to-worker handshakes and readiness must fail closed: an accidentally outdated or
incompatible worker is unschedulable rather than receiving work that may fail later. Supporting
rolling N/N-1 worker or API upgrades within the stable 1.x line is a separate post-1.0 decision;
this migration does not carry alpha protocols merely to provide it.

Silo's standing release policy requires a verified backup before every upgrade and does not
guarantee downgrade or in-place rollback compatibility between releases. For 1.0, the final
dual-stack bridge remains published as an immutable recovery artifact. The supported recovery path
is to stop 1.0, restore the complete pre-upgrade database and configuration, and deploy that bridge;
post-backup changes are lost. Administrators must not start the bridge against a database migrated
or written by 1.0 unless release notes explicitly certify that exact combination. The bridge
receives no continuing development after cutover.

The 1.0 cutover closes after the homogeneous fleet, root probes, v2 client smoke tests, regenerated
external integrations, and v1 tombstone isolation all pass. The bridge artifact may remain
downloadable without becoming another supported API line or implying a guaranteed downgrade path.

## Tiered legacy native behavior and performance baseline

The route and consumer inventory is exhaustive; behavioral baselining is not. Recording every
observable case of every legacy native route would spend the migration budget documenting alpha
behavior that v2 is free to redesign. Baselining is therefore tiered.

Tier 1 is the release-critical flows — login, setup, profiles, browse/search, playback lifecycle,
progress, settings, notifications, downloads, and core admin — plus every `ported`-disposition
ledger row whose wire fidelity matters to a shipping client. Each tier-1 row carries a scenario
catalog of executable assertions covering its applicable status and header behavior, data meaning,
field presence and nullability, authorization, sorting, filtering, pagination, error behavior, and
relevant raw-protocol behavior. Those catalogs prioritize the risky wire shapes: anonymous maps,
`json.RawMessage`, custom marshalers, timestamps, nullable and optional fields, empty collections,
multipart bodies, redirects, ranges, and every distinct error code, status, and header combination.
Every other route defines its v2 behavior fresh in its own section PR with ordinary tests; there is
no obligation to first document what its alpha predecessor did. V2 is never required to reproduce
pre-1.0 bytes or accidental alpha shapes. A tier-1 section either proves the intended product
behavior or records a reviewed intentional difference in the migration ledger.

Inventory itself stays exhaustive and searches repository-wide path literals, regular expressions,
and route classifiers, not only handler registrations. API-key scope checks, demo mutation guards,
compression/sendfile exclusions, request/activity logging, telemetry labels, compatibility URL
builders, and other internal consumers move to stable operation or route metadata where practical
and receive parity tests. A registered-route ledger that leaves stale middleware patterns behind is
incomplete.

Every comparison run happens in one controlled bridge environment. The legacy native surface and v2
are exercised against the same candidate build, representative non-sensitive dataset,
configuration, cache state, and concurrency, covering mutations, negative and error cases, races,
cold and warm cache states, and load. That same-environment comparison — not a comparison between
unrelated production and test hosts — supplies the regression evidence. There is no
live-deployment observation harness, no raw production capture, and no custody process to go with
them. All committed evidence is synthetic: scenario definitions, deterministic synthetic fixtures
and assertions, and measurements from the controlled environment. A live response is never
converted into a committed fixture.

Behavior checks assert domain outcomes rather than wire equality. For example, a recently released
catalog query proves ordering by the intended release value, direction, null placement, stable
tie-breaker, access filtering, and pagination without duplicates or gaps. Catalog scenarios cover
each sort field in both directions, each filter independently, and a curated set of representative
and pathological combinations — null-heavy sorts with pagination, filters with tie-breakers, empty
results with cursors — plus empty, sparse, and large result sets. An intentional v2 correction
records the previous behavior, the new expected behavior, and its rationale in the ledger.

Performance evidence is scoped to a named hot-path list: catalog list/search, home sections,
playback start/replan, progress writes, and jellycompat browse. Those paths record p50/p95/p99
latency, throughput, response size, allocations, and database-query behavior at representative
concurrency under controlled cold and warm cache states. Other operations rely on the correctness
tests in their section PR. Streaming and byte delivery are measured separately with protocol
throughput tests because they bypass Huma. A repeatable regression is investigated; the
program-wide quantitative threshold and hot-path budgets are agreed before any v2 measurements
are taken, so results cannot be rationalized after the fact, and sections may adopt stricter
budgets.

## Evolution policy

Before the v2 lock, a breaking v2 change is allowed only when its migration-ledger entry, generated
spec diff, fixtures, client impact, and release consequence are reviewed together. A route is not
“done” merely because its server handler exists.

At the Silo 1.0 lock, `/api/v2` becomes additive-only and binding:

- do not remove or rename an operation, parameter, response field, error code, operation ID, or
  schema name;
- do not narrow accepted input, change a field's type or meaning, or repurpose a status code;
- add fields and enum values in ways lenient clients can tolerate, and advertise new behavior with
  capability documents;
- retire behavior only through the project's `Deprecation`, `Sunset`, and `Link` header flow;
- require a new API major for a change that cannot obey those rules.

CI reproduces the spec and uses an OpenAPI semantic diff against the merge base. After lock, an
unapproved breaking diff fails without an override path. Before lock, approved breaks are exact,
machine-readable entries tied to the affected operation; a prose note cannot authorize an
unbounded diff.

## Release gates

The v2 contract may lock only when all of the following are true:

- every registered route in the legacy native surface has a reviewed v2 disposition, including
  API, proxy, transcode-node, conditional, binary, WebSocket, redirect, asset, internal-control,
  and plugin-proxy routes;
- every externally provisioned or persisted legacy native URL is mapped to its v2 replacement and
  to the exact administrator action needed after cutover; root `/health` and `/ready` are verified
  independently of the `/api/v1` tombstone;
- the main API listener's tombstone tests cover the exact `/api/v1` and `/api/v1/` roots plus descendants across
  representative methods, including the bodyless `HEAD` response and documented `OPTIONS`
  behavior; every case returns `410`, never reaches auth/business/proxy code, and uses `no-store`;
- every v2 JSON operation is Huma-typed and appears in the deterministic OpenAPI artifact;
- the shared error and validation contract is exercised through every middleware class;
- generated web types are the only web definitions for v2, with no unchecked v2 response casts;
- Apple and Android have vendored their consumed release-candidate fixtures, pin the frozen server
  commit in `SOURCE`, and pass their conformance suites;
- no first-party client contains a legacy native transport path in its release build;
- the new-client/v1-only-alpha update-required, new-client/bridge, new-client/1.0,
  old-client/bridge, and old-client/1.0-tombstone cases have been tested;
- compatibility listeners, plugin RPC, streaming/range behavior, WebSockets, auth boundaries, and
  request limits have regression evidence; every tier-1 scenario catalog passes or records its
  reviewed intentional difference, and every named hot path passes the agreed
  controlled-environment performance budgets;
- repository-wide legacy path literals and classifiers are migrated or explicitly retained, with
  API-key scope, demo guard, compression/sendfile, logging/activity, telemetry, and compatibility
  URL-builder parity proven;
- spec reproducibility, semantic diffing, fixture freshness, and migration-inventory completeness
  are required server checks; cross-client source pins are verified at the 1.0 release gate;
- the third-party migration guide and v1 retirement notice are published;
- the administrator update-to-1.0 guide covers integration reconfiguration, invalidated links,
  active transfers/playback, plugins, probes, validation, and recovery preparation;
- the complete pre-upgrade restore, bridge redeployment, and 1.0 go/no-go procedures have been
  rehearsed.

## Consequences

The reset removes the need to prove byte-for-byte equality between v1 and v2. The relevant proof
is stronger and more useful: every old operation is accounted for, every new operation is
machine-described and tested, intentional differences are visible, and every shipping client has
demonstrated the contract it consumes.

The cost is a coordinated multi-repository release and a temporarily larger server. Keeping the
bridge bounded, sharing domain services, and making each migration slice include its consumers are
what prevent that temporary cost from becoming permanent architecture.
