# Interface translation

Every Silo client (web and web admin, Apple iOS/tvOS/macOS, Android phone and TV, Roku) takes
its converted interface text from one English catalog and its translations. This page records who owns
that text, the rules a message must follow, how each client chooses a language at runtime, and
how text the server sends is translated. Metadata translation (`catalog.metadata_language` and
AI description translation) is a separate feature; see [the catalog API](../catalog-api.md).

## Catalog ownership

`Silo-Server/silo-translations` owns every interface string. Its `catalog/en.arb` is the English
source: each key carries its message and metadata (a `description` of where the text appears and
what each placeholder holds, typed `placeholders`, optional `x-platforms` and `x-maxLength`).
`catalog/<lang>.arb` holds translations, and `locales.json` lists the languages with their
per-platform identifiers. That repository's README is the full reference for keys, messages and
generated output, and its CONTRIBUTING covers translators and the machine translation pass.

Its generators turn the catalog into each client's native format:

| Client | Generated files |
|---|---|
| web (this repository) | `web/src/locales/<tag>.json` (precompiled FormatJS messages), `web/src/locales/keys.ts` (`MessageKey`, `LOCALES`) |
| silo-apple | `iosApp/iosApp/Localizable.xcstrings`, `iosApp/InfoPlist/{iOS,tvOS,macOS}/InfoPlist.xcstrings` |
| silo-android | `android-shared/src/androidMain/res/values{,-<qualifier>}/strings_catalog.xml`, `android-shared/silo-locales.properties` |
| silo-roku | `locale/<folder>/strings.json`, `locale/languages.json`, `source/util/pluralRules.bs` (CLDR plural rules), `i18n-charsets/<folder>.txt` |

Each client vendors the catalog's `tools/sync-translations.sh` as `scripts/sync-translations`
and keeps the copy identical to the catalog's current script. It installs a pinned release
(`--version <release>`) or the output of a local catalog checkout (`--local <checkout>`), and
records the platform, version and checksum in `.silo-translations`. The current script also
records the installed paths in `.silo-translations-files` and removes files that a language
which stopped shipping left behind; a client still on an older copy keeps those files until it
re-vendors. It installs only the platform's generated outputs and refuses a release whose
file list names anything else. The generated files are committed with
those two records, so a client build never runs the generator.

Never edit generated files. Change the catalog, then sync.

## Keys

- Keys are dot-separated segments. Each segment matches `[a-z0-9][A-Za-z0-9_]*` and the first
  starts with a letter. Named segments are lowerCamel (`home.section.continueWatching`). A
  segment built from a server identifier keeps the identifier, with `-` turned into `_`
  (`settingsManifest.ui.theme.option.midnight_cinema`), so a client can build the key from
  the value it holds.
- A key that is not a plural cannot end in a CLDR plural category (`zero one two few many
  other`), because Roku writes plural forms as `key.<category>`.
- Platform names are derived mechanically: Android replaces `.` with `_`
  (`home_section_continueWatching`), Apple's symbol joins the segments in lowerCamel
  (`.homeSectionContinueWatching`), and web and Roku use the key itself. The validator
  rejects keys that collide on any platform (`home.sectionTitle` and `homeSection.title` are
  the same Apple symbol).
- Namespaces follow the feature, not the platform:
  - `common.*` holds vocabulary every client shares.
  - Apple, Android and Roku share feature namespaces (`player.*`, `detail.*`, …), so one key
    serves every native app that shows the same text.
  - Web text is under `web.<area>.*`, scoped to web, because most web screens have no native
    counterpart.
  - Web admin text is under `web.admin.*`. The web serves it as a separate catalog part that
    loads only for admin pages, the setup wizard and an administrator's session, so text a
    non-administrator can see uses `web.common.*` (any user) or another area, never
    `web.admin.*`. Admin-only text shared by several admin pages is `web.admin.common.*`.
  - Server text has fixed namespaces: `home.section.*`, `home.recipe.*`, `error.*`, `error.field.*`,
    `settingsManifest.*` (see [Server-provided text](#server-provided-text)).
  - Apple permission prompts are `apple.infoPlist.<ios|tvos|macos>.<name>`, with the plist key
    in `x-plistKey`.
- `x-platforms` limits a key to some of `web`, `apple`, `android`, `roku`; omitted means every
  client. A generator emits only the keys in its platform's scope. Reuse an existing key only
  when its English and its meaning both match; to reuse one scoped elsewhere, add your
  platform to its `x-platforms`.

## Messages

Keys that reach Apple, Android or Roku use a subset of ICU MessageFormat that every target can
express:

- Text and `{name}` placeholders. Each placeholder is declared with a type (`String`, `int` or
  `double`) and a name matching `[a-z][a-z0-9_]*`. Declaration order is the positional order on
  Apple (`%1$@`) and Android (`%1$s`), so existing placeholders are never reordered, and a key
  with two or more placeholders names them in order in its description.
- At most one `plural`, spanning the whole message, on an `int` argument, with exactly the CLDR
  categories of the language (`es`, `fr` and `pt-BR` need `many`; `ar` needs all six) and `#`
  for the number. ICU groups `#` (`1,000`), so a count that can pass 999 selects on the number
  and prints a separate `String` placeholder inside the forms.
- No `select`, `selectordinal`, `=N`, `offset`, typed arguments (`{n, number}`, dates) or tags.
  Callers format dates, sizes and durations and pass them as `String`. Web-only keys may also
  use `select` and rich-text tags.
- A possessive is one whole message with the owner as a placeholder (`{name}'s devices`), so a
  translator can restructure it. Code never builds a possessive by concatenation.
- Prefer the typographic apostrophe `’`. An ASCII `'` is accepted where ICU reads it literally
  (`Couldn't`, `{name}'s`) and rejected directly before `{ } # | < '`, where ICU starts an
  escape.

**Data stays English.** Text that is stored, sent to the server, matched or compared is data,
not interface text, and stays English in every language: values written to settings, saved row
names and labels, track signatures, and server text the client compares against. Only text
that is shown is translated. When a shown label and a stored value come from the same code,
split them. Web code formats data text with `englishText()` from `@/i18n`. Server-generated
names such as device names ("Chrome on Linux") are server data and stay English.

## Choosing the language at runtime

### Precedence and catalog gating

Each client resolves one interface language, highest precedence first:

1. The profile's effective `ui.app_language`, when it matches a language the client supports.
2. The device or browser language list (on Android 13+, iOS and macOS this includes the
   system's per-app language for Silo), matched only against languages whose translations
   have shipped in that client.
3. English.

A language ships in a client once the generated output contains it, which happens when it has
at least one translation in that client's scope. Every client reads the shipped list
from the generated output: the web from `LOCALES` in `web/src/locales/keys.ts`, Roku from the
languages whose generated table has strings. A device or browser in an untranslated language therefore keeps the
English interface. A stored choice selects any language the client supports. On Android and
Apple that is the shipped list. The web supports the languages in `SHIPPED_LANGUAGES` and Roku
those in `i18n.languages()` (`source/util/i18n.bs`), translated or not. A stored untranslated
language then shows English text, on the web with that language's direction and formatting. Pickers list English, the shipped languages, and the stored tag when the client does
not ship it (shown by its language name), so re-saving never clears another client's choice.

Before sign-in (server picker, login, setup) a client uses the device list and the last
override it applied, cached locally and cleared when a profile follows the device. The web's
signed-out language menu applies only until a profile's setting loads, then it is cleared.

### Matching

A regional tag matches its language, and Chinese matches by script. Every client gives the same
answers for these: `es-MX` → `es`; `pt` and `pt-PT` → `pt-BR`; `zh`, `zh-CN` and `zh-SG` →
`zh-Hans`; `zh-TW`, `zh-HK` and `zh-Hant` match no shipped language, so resolution moves on to
the next candidate and finally English. The same rule applies to stored values and to the
device or browser list. The implementations differ at the edges:

- Web compares language and script after maximizing both tags (CLDR likely subtags).
- Android and Roku try an exact match, then the language alone, comparing the script only for
  Chinese.
- Apple uses `Bundle.preferredLocalizations(from:forPreferences:)` against the bundle's
  localizations.

Pseudo-locale tags select a pseudo-locale only in builds that carry them. Android never matches
them to a real language. On the web and Roku a pseudo tag in a build without pseudo-locales
falls back by language (`en-XA` → English, and on the web `ar-XB` → Arabic).

### `ui.app_language`

The setting is defined in `contracts/settings/v1/manifest.json` and documented in
[the settings API](../settings-api.md):

- A nullable `language_tag`, canonicalized on write (`pt_br` is stored as `pt-BR`). `null`, the
  default, means follow the device; the manifest's `unset_label` is "Match device". `""` is
  rejected; clear an override by writing `null` or with `DELETE`.
- Scopes `profile` and `profile_device`, resolved `profile_device` → `profile` → `default`. An
  effective read therefore needs `X-Silo-Device-Id`.
- An open tag, so adding a language needs no server release. The `app_languages` option set is
  only the list the generic admin control suggests.
- The in-app picker writes `profile` scope, so the choice follows the person across devices,
  and deletes this device's `profile_device` row so it applies here too (Android and Apple do
  this; web and Roku write `profile` scope only). "Match device" writes `null`.
- On Android 13+, iOS and macOS the profile's language and the system per-app language are one
  setting. Applying a profile's language also writes the system value. A change the user makes
  later in system settings is detected at launch and written back as this device's
  `profile_device` value. A profile with no value restores the system value from before Silo
  changed it; an explicit "Match device" clears Silo's own system value.
- When following the device, web, Apple and Roku apply the language the device list resolves
  to as an explicit display language, not whatever locale the process inherited. Android leaves
  resource resolution to the framework.

### Formatting locale

Dates, numbers and lists use the platform's locale formatting, and the rule for choosing that
locale differs by client:

- **Web:** with no stored choice, or when the browser's default already speaks the chosen
  language, format with the browser default; otherwise with the stored tag. Choosing English on
  an `en-GB` browser keeps British dates. Words inside formatted output (list conjunctions,
  relative times, language names) follow the interface language. The DD/MM date-order
  preference controls numeric dates in every language, and month-name dates follow the
  language's own order (`en-GB`/`en-US` for English).
- **Apple:** the chosen language with the device's region and hour cycle.
- **Android:** the applied resource locale.
- **Roku:** the platform date formatters use the device locale. Dates built from catalog keys
  (month names and a month-day template) follow the applied catalog.

### Right-to-left isolation

In a right-to-left interface, clients wrap placeholder values in Unicode isolates (FSI…PDI) at
format time, so a left-to-right title keeps its punctuation in place. Web isolates every
printed string placeholder (not `select` or `plural` selectors). The native clients isolate
title and name placeholders where the call site asks for it: Android through
`stringResourceWithNames()`, Apple through `AppLanguage.isolated(_:)`, and both for section title
arguments. A plain Android `stringResource` call does not isolate. Left-to-right output, English
included, keeps its bytes.

### `Accept-Language`

Clients send `Accept-Language` with one tag: the language on screen. It is a hint for text the
server renders for that request. Server text bound to a profile rather than a request uses the
profile's `ui.app_language`, not the header. No server response depends on the header today,
so none sends `Vary: Accept-Language`; a response that comes to depend on it must. The plugin
route proxy forwards the header to plugins.

## Server-provided text

The server sends English. A client shows the catalog's translation of server text in a
non-English interface when that language has one; otherwise it shows the server's text. Clients
differ in how strictly they hold to that:

- Web and Apple show the server's text exactly as sent in English, when the language lacks the
  key, and when an argument the message needs is missing.
- Android does the same for problem details. For section titles it uses the string resource,
  which is the catalog's English when the language lacks a translation (the same text as a keyed
  default title), and keeps the server's `title` when the arguments don't fit the message.
- Roku reads a table that merges the language over English. A section title or problem in an
  untranslated language therefore shows the catalog's English: the same text for a keyed
  title, but generic `error.*` text instead of the server's `detail` for a problem. Roku keeps
  `detail` in English, and leaves a placeholder unfilled when `title_args` lacks its value.

### Section titles

v2 sections and profile section settings carry optional `title_key` and `title_args` while the
row's `title` is the server's own text, a built-in or generated row name. `title_key` is a
`home.section.*` catalog key, and `title_args` fills its placeholders by name
(`home.section.recentlyAddedIn` with `{"library": "Movies"}`). [The catalog API](../catalog-api.md)
lists which responses carry them and when they are absent. Clients act on the fields' presence;
the `section_title_keys` home capability is informational.

`page_sections.title_key` stores the key beside the title. A trigger clears it when an update
changes the title without setting a new key, so telling a default from a rename never compares
text. The keys are defined in `internal/sections/title_keys.go` and, for recommendation rows,
`internal/recommendations/titles.go`; a seasonal row's built-in title, a recipe preset's text and a
Requests Discover row's default title are keyed in `internal/sections/recipes/text_keys.go` and
`internal/requests/discoverrows/defaults.go`. A section key has at most one placeholder: Apple and
Android fill arguments by position, and with one placeholder the name-to-position mapping is
unambiguous.

### Problem details

v2 [Problem Details](api-contract.md#problem-details) carry no translated text. In English a
client always shows the server's `detail`. In another language it shows `error.field.<code>`
for the field error it reports, then `error.<type>`, when the catalog has it, else `detail`.
`error.<type>` exists for every type in the problem catalog in `internal/apiv2/problem.go`, and
`error.field.<code>` for every field-error code defined there, plus `invalid_sort_field` and
`invalid_entity_tag`, so a new type or code needs its catalog key. `path_rewrite_required` has
none: its `detail` names the source root that needs a rewrite, which a fixed message would hide. Their text stays generic. A screen that needs specific wording uses its own key,
chosen by status. Client code never branches on the translated text.

### Settings manifest

Labels, descriptions, unset labels and option labels from
`contracts/settings/v1/manifest.json` become `settingsManifest.<settingKey>.label`,
`.description`, `.unsetLabel` and `.option.<value>`. silo-translations imports them from a pinned
copy of the manifest and its check fails on drift. Change the English here, in the manifest,
then re-import with `make import-settings-manifest REPO=<silo-server checkout> REF=<commit>` in
silo-translations; never edit those keys in the catalog. The generator scopes each kind: web
and Apple get all of them, Android only `unsetLabel`, Roku none. At runtime the web looks
labels up by setting key (`web/src/lib/settingsText.ts`), Apple translates unset labels, and
other manifest text reaches native screens as the manifest's English.

### Not translated

Server-rendered email, push and webhook text is English. Jellyfin clients translate their own
interface; jellycompat does not translate.

## Platforms

| Client | How it applies the language | Limits |
|---|---|---|
| Web | `LocaleProvider` sets `<html lang dir>` and loads the language's messages on demand. | Guide: `web/src/i18n/README.md`. |
| Android | `LocaleManager` on Android 13+; before 13, a wrapped activity context. `localeFilters` come from `android-shared/silo-locales.properties`. | Android TV has no system per-app language screen; the in-app picker is the only one. |
| Apple | `.environment(\.locale)` and `.environment(\.layoutDirection)` at the SwiftUI root, plus the app's own `AppleLanguages`. | System UI follows after the next launch. Subtitle fallback keeps reading the device's language list. |
| Roku | The profile's value applies before the first screen; otherwise `GetCurrentLocale()` is matched. | No `ar` (no right-to-left layout or Arabic shaping). Japanese and Chinese use a Noto subset built from `i18n-charsets/`, since SceneGraph has no font fallback. |

Each client documents its call sites: `web/src/i18n/README.md` here, `docs/i18n.md` in
silo-android and silo-apple, and "Translations" in silo-roku's `docs/development.md`.

Pseudo-locales are generated for debug builds: `en-XA` (accented and longer) for web and Roku,
`ar-XB` (right-to-left) for web only. On web, `vite dev` and builds with
`VITE_PSEUDO_LOCALES=1` include them.
Android and Apple use their platform's own pseudo-locales.

## Adding a string

1. In silo-translations, add the key, English message and metadata to `catalog/en.arb`: a
   `description`, typed `placeholders`, and `x-platforms` when only some clients use it. Follow
   [Keys](#keys) and [Messages](#messages). Run `make fmt` and `make check`.
2. In the client, run `scripts/sync-translations --local <silo-translations checkout>` while
   the catalog change is unmerged, and `--version <release>` once it has a release. Commit the
   generated files, `.silo-translations` and `.silo-translations-files` with the code that uses
   the key.
3. Use the key through the client's API (see each client's guide). Never put English in client
   code: the web has no `defaultMessage`, and English comes from the generated `en` output.
4. Add no translations. The translation pass writes them, and a key without one shows English.

Moving an existing string into the catalog keeps its English byte-identical; wording changes go
in their own pull request.

Server-side additions follow the same path: a new default section title gets a
`home.section.*` key and its constant in `internal/sections/title_keys.go`, a new problem type
or field code gets its `error.*` key, and a manifest label change is re-imported.

Translators correct or add translations in `catalog/<lang>.arb`; silo-translations'
CONTRIBUTING describes that and the style guides.

## Adding a language

1. In silo-translations, add an entry to `locales.json`: the BCP 47 `tag`, its `name` in itself,
   `dir`, the `cldr` plural-rules locale, the Android resource qualifier, the Roku folder, and
   `platforms` when a client must not ship it yet. Add `style/<tag>.md` and the language's
   `glossary.csv` column, then run the translation pass (`make translate LOCALE=<tag>`).
2. Sync every client. Android's `localeFilters` and generated `localeConfig` and Apple's bundle
   localizations pick the language up from the generated output. Two clients keep their own
   lists:
   - Web: add the language, its endonym and direction to `SHIPPED_LANGUAGES` in
     `web/src/lib/appLocale.ts`, and its CLDR display-name data to `NAME_DATA` in
     `web/src/lib/languageNames.ts`. The pickers offer it once the generated `LOCALES` lists it.
   - Roku: add it to `i18n.languages()` in `source/util/i18n.bs`.
3. Check the platform limits: a right-to-left language does not ship on Roku, and a script the
   Roku fonts don't cover needs its own font subset.
4. Optionally add the tag to the `app_languages` option set in
   `contracts/settings/v1/manifest.json` (a manifest revision bump), so the admin control
   suggests it.
