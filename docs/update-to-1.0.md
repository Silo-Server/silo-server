# Update an alpha installation to Silo 1.0

**Status: draft administrator checklist. The receiver paths below are taken from
`contracts/api/v2/openapi.json`; the exact release commands, image tags, and
administration-UI locations are still to be filled in before release.** Commands assume the
repository root is the cwd.

This guide is for administrators moving a pre-1.0 Silo installation to Silo 1.0. The native API
changed from the alpha contract to the stable `/api/v2` contract. The alpha native surface
included `/api/v1` and version-neutral paths served by the proxy and transcode-node listeners.
Silo retains no aliases for either class.

`/api/v1` is already retired before 1.0. The pre-1.0 release that removes it answers every
`/api/v1` route with a retirement tombstone, so the integration, URL, and client steps below apply
when a deployment updates to that release, not only at 1.0. A deployment that completed them then
does not repeat them for 1.0. A fresh deployment is recommended where practical. Existing
installations use a maintenance window; zero-downtime updates across the v1 retirement or to 1.0
are not supported.

1.0 is not reachable directly from an arbitrary alpha build. Existing installations update
0.x → the final pre-1.0 release → 1.0. The final pre-1.0 release is the last one that carries the
full historical migration chain, the Go data migrations, and the one-way SQLite-to-Postgres
per-user store import. Silo 1.0 ships one squashed schema baseline behind a guard that accepts only
an empty database or a database left at exactly the final pre-1.0 release's last migration
version; anything else refuses to start and tells the administrator to update to the final
pre-1.0 release first.

Silo's general release policy requires a verified backup before every upgrade and does not
guarantee downgrade or in-place rollback compatibility between releases. See
[release versioning](release-versioning.md#backups-and-rollback). The 1.0 procedure below follows
that same rule rather than creating a special downgrade promise.

The architecture and rationale are recorded in
[the native API contract](architecture/api-contract.md). Release notes remain authoritative for
the exact image tags, database compatibility, and commands for a particular build.

## What stops working when `/api/v1` retires

On a server without v1, `/api/v1`, `/api/v1/`, and their descendants on the main API listener
return `410 Gone` with the `client_upgrade_required` error code and run no old business handler.
This retirement tombstone does not handle routes on the proxy or transcode-node listeners. Some
pre-1.0 stream, download, proxy, transcode-node, and internal-control routes are version-neutral;
each was moved, retained, or retired individually without an alias, and a retired one is not
promised the same `410` response.

Together, these changes invalidate structured client calls and URLs generated by an alpha server
that served v1, including:

- active playback and stream URLs;
- queued or resumable downloads, download manifests, artwork, and subtitle URLs;
- plugin HTTP routes and plugin asset URLs;
- autoscan and webhook-sync receiver URLs configured in another service, including the legacy
  Plex-sync receiver, which has no v2 successor of its own;
- OAuth and browser callback URLs registered with an identity provider;
- Discord-link callbacks and similar integration callbacks;
- verification, unsubscribe, invitation, or other tokenized links sent before the upgrade.

Silo does not redirect these URLs. Some contain bearer tokens or secrets that must not be copied
into a redirect location. Generate new URLs from the updated server instead of editing an old
path by hand.

Operational probes are the exception to the versioned namespace and are not tombstoned. Silo
retains `GET /api/v1/health` and `GET /api/v1/ready` on the API listener and `GET /api/v1/health`
on the proxy and transcode-node listeners unchanged; no root `/health` or `/ready` route is added.
Existing probe configuration keeps working.

## Beta Books functionality

Silo 1.0 supports Movies and Series. Audiobooks, ebooks, and Audiobookshelf
compatibility remain available and unchanged on 1.0 builds, labeled
**beta** and outside the 1.0 support promise. A consolidated Books effort will
replace them later, with no assigned release date. See the
[scope decision](architecture/v1-scope.md#library-scope-books-deferred).

Upgrading to 1.0 does not change, gate, or remove these libraries, their
progress, or the Audiobookshelf endpoint. No data migration is required for
them. Release notes must state that they are beta, not that they are
unavailable.

## Before updating

- [ ] Read the release-specific notes and confirm that the server, database, Redis, object
  storage, reverse proxy, and remote-node versions are supported together.
- [ ] Confirm the deployment is running the final pre-1.0 release and that its database
  migrations have finished before deploying 1.0. The 1.0 startup guard refuses a database that has
  not reached that release's last migration version.
- [ ] Back up PostgreSQL using the deployment's normal tested procedure, and verify that the
  backup can be restored. Silo takes its own database backup before startup migrations when
  backups are on (see [before upgrades](architecture/backups.md#before-upgrades)), but that copy
  stays at the backup destination, by default on the same server, so keep an off-server copy too.
- [ ] If `userdb.backend=sqlite` is configured, back up the local SQLite user store at
  `/var/lib/silo/userdb` with the same care and verify it can be restored. The final pre-1.0
  release's one-way SQLite-to-Postgres import reads this data; losing the directory loses profiles and per-user
  state. Confirm the path is persisted by the deployment — the default Compose file does not
  persist it (see the deployment guide).
- [ ] Preserve the current server configuration, secret material, deployment manifests, and the
  exact final pre-1.0 server image or binary needed for the documented recovery procedure.
- [ ] Record the public Silo URL and every reverse-proxy or load-balancer route that refers to
  `/api/v1`, `/stream`, `/downloads`, `/transcode`, or another alpha-native path named in the
  [integration checklist](#integration-checklist).
- [ ] Inventory every external service configured with a Silo callback or webhook URL. Common
  examples are Sonarr/Radarr autoscan, the legacy Plex-sync receiver, webhook sync, OAuth
  providers, and notification integrations.
- [ ] Inventory installed plugins and any plugin-provided pages or links used outside the bundled
  web application.
- [ ] Record health/readiness probe configuration for containers, Kubernetes, load balancers,
  uptime monitors, and remote nodes.
- [ ] Finish or pause active playback and downloads. Expect unfinished jobs to be restarted after
  the update.
- [ ] Drain and stop every API replica, proxy/playback node, and remote transcode node. Do not
  leave alpha and 1.0 components in the same active fleet.
- [ ] Make the matching 1.0 builds available for every Apple, Android, Android TV, Apple TV, and
  other native client that will connect after cutover.
- [ ] If users are waiting on verification, invitation, unsubscribe, or other emailed links,
  expect to resend them after 1.0 is running.
- [ ] Optional: copy the `cap_add: [NET_ADMIN]` line and its comment from the new
  `docker-compose.yml` into your Compose file. With it, Silo uses kernel BBR on its client
  connections and a larger TCP send buffer for remote clients on long, fast links. Read its risk
  in [TCP congestion control](architecture/tcp-congestion.md) first. Without it, Silo still asks
  for BBR where the host allows it, keeps the kernel's send buffer limits, and logs at start what
  it could not change and how to fix it.

## Perform the update

1. If the deployment is not already on the final pre-1.0 release, update to it first,
   following its own release notes, and let its database migrations finish. Verify it is
   healthy before continuing; 1.0 accepts only a database left at that release's last migration
   version.
2. Stop or drain the entire alpha deployment according to the release-specific instructions,
   including every API replica and remote playback/transcode node.
3. Deploy the matching Silo 1.0 API, proxy, and worker components and run only the documented
   database migration procedure. An incompatible node must remain unschedulable. Remote
   transcode nodes start with new settings; follow [Transcode nodes](#transcode-nodes).
4. Keep operational checks on `GET /api/v1/health` and `GET /api/v1/ready` (and node
   `GET /api/v1/health`); these probes are retained unversioned and are not redirected or
   tombstoned.
5. Update the bundled web deployment and all first-party native clients to their matching 1.0
   builds.
6. Existing login sessions, refresh tokens, profile security state, and API keys remain valid
   until normal expiry or revocation. Sign in again only when the normal session flow requires it.
   Opening plugin content through 1.0 reissues its separate five-minute access cookie on the v2
   path.
Steps 7 to 11 are the v1-retirement steps. A deployment that completed them when it updated to
the pre-1.0 release that retired `/api/v1` skips them here; otherwise run them now.

7. Open each integration in the 1.0 administration UI, regenerate or copy its new callback URL,
   and save that URL in the external service. Rotate a token or secret when the UI offers that
   operation.
8. Reconnect OAuth-backed authentication or notification integrations so the provider records the
   1.0 callback URL.
9. Open every installed plugin page through the 1.0 UI. Refresh or reinstall a plugin when its
   own release notes require a version compatible with Silo 1.0.
10. Restart downloads and playback instead of attempting to resume an alpha-issued URL.
11. Resend any pre-1.0 tokenized email action that still needs to be completed.

## Transcode nodes

Remote transcode nodes (`MODE=transcode`) no longer connect to PostgreSQL or Redis and no longer
use the shared `SECRET_KEY`. Each node starts with two settings, `SILO_CORE_URL` and
`SILO_NODE_KEY`, and takes everything else from the main server. The update is coordinated: a
transcode node from an earlier release cannot work with an updated main server, and an updated
node cannot work with an earlier main server. Proxy nodes keep their current settings.

1. Stop every transcode node. Drain it first if it still runs playback (see
   [node drain](architecture/node-drain.md)).
2. Update the main server, every API replica, and every proxy node, and let the migrations finish.
3. Issue each transcode node a key: on the nodes page of the administration UI, or with
   `POST /api/v2/admin/nodes/{id}/key`. The key is shown once. Issuing again replaces it, and the
   previous key stops working at once. A node still running with the replaced key shuts down at
   once on SIGTERM instead of waiting for its sessions, which the main server can no longer reach,
   so restarting it with the new key does not wait for the drain timeout.

   A deployment managed from configuration can then hand these keys to its configuration: keep
   each issued key in your secret store, list the nodes in the main server's
   `SILO_TRANSCODE_NODES` or `SILO_TRANSCODE_NODES_FILE` with a reference to that key, and restart
   the main server and every API replica. Each listed node is adopted, and from then on its key
   comes from the configuration. A node added later skips the administration UI: write its key
   with `silo node-key generate --id <n>` for an id above every node id the server has handed
   out, and list it the same way; the API servers create it when they start. An existing node
   needs its key from the administration UI, because a node that exists with no key or another
   key stops the API server.
   See [declared nodes](architecture/transcode-nodes.md#declared-nodes).
4. Update each transcode node and start it with:
   - `MODE=transcode`;
   - `SILO_CORE_URL`, the main server's URL as the node reaches it (the load-balanced address when
     there are several API replicas);
   - `SILO_NODE_KEY`, the key from step 3.

   Optionally, the node can declare its own name, URL, group, transcode limit, source access,
   acceleration and download storage with `SILO_NODE_*` variables; the nodes page then shows those
   fields read-only. See
   [node-declared configuration](admin-api.md#node-declared-configuration). Set
   `SILO_NODE_URL` and `SILO_NODE_NAME` for each node separately: unlike `NODE_URL` and
   `NODE_NAME` below, a transcode node acts on them, so a value copied from a proxy's `.env`
   would point the transcode node's entry at the proxy.

   The node ignores `DATABASE_URL`, `REDIS_URL`, `SECRET_KEY`, `NODE_URL`, and `NODE_NAME`, with
   one warning at startup, so they can stay in a shared `.env`. The shipped `docker-compose.yml`
   still asks for a `SECRET_KEY` value; the node does not use it. A node on the bundled image no
   longer needs the main server's PostgreSQL or Redis ports; turn node access off once no proxy
   uses them.

The network between the main server and its transcode nodes must allow both directions: the
node calls the API at `SILO_CORE_URL`, and the API servers and proxies call the node at its
registered URL. The node takes its FFmpeg path, directories, and input paths from the main
server's answers, so the link must be a trusted network or `SILO_CORE_URL` must use `https://`; the
node logs a warning at startup for a plain-HTTP URL that is not loopback. A reverse proxy in front
of the API must pass `/api/internal/nodes/` with the path, query, body, and `Authorization` and
`X-Silo-Source-Grant` headers unchanged (it may strip a path prefix that is part of
`SILO_CORE_URL`). These requests are small JSON documents of at most 1 MiB that complete within 10
seconds, except `/api/internal/nodes/sources`, which streams source media to nodes that read
through the main server (below). The clocks of the
nodes and the API servers must agree within 30 seconds: a node whose clock is further off has every
request refused and reports its key as rejected, which a new key does not fix.

Every API server must see each library file at the same path with the same size and modification
time, as they already had to see the same paths. A transcode node that reads its own library mount
must see each file at the same path with the same size; its mount may report other modification
times. A node whose mount lacks the file or shows another size refuses the job and logs both sides.

### Source access

Each transcode node has a source access setting, on the nodes page or as `source_access` in
`PUT /api/v2/admin/nodes/{id}`:

- `local`, the default, reads media from the node's own library mount, as above.
- `core` reads media over HTTP from the API servers. The node needs no library mount, which suits
  a GPU machine that cannot mount the library. Every byte the node reads passes through the API
  servers, so they need that bandwidth on top of what they already serve: a node transcoding a
  remux reads its full bitrate for every session. `silo_node_source_bytes_sent_total{node}` on
  each API server shows what each node costs. The node applies a change to the jobs it starts
  afterwards; running jobs keep their mode.

A node host with `http_proxy` set needs nothing special for `core`: the node reads source bytes
from the API servers without a proxy, and FFmpeg reads from the node's own loopback relay without
one.

Choose `core` when mounting the library on the node is impractical, and `local` when it is easy
or the API servers' network is the bottleneck. A text subtitle burn-in that cannot be staged from
the file's index does not run on a `core` node; the start moves to a `local` node or the main
server.

A reverse proxy in front of the API must not buffer `/api/internal/nodes/sources` responses and
needs long read and send timeouts on that location: a response streams for as long as FFmpeg
reads, and the node resumes a cut one. It must pass `Range` and `If-Match` through and must not
compress the response. Each API server serves one node at most 512 of these streams at once and
answers `429` past that, which the node retries. For nginx:

```nginx
location /api/internal/nodes/sources {
    proxy_pass http://silo_api;
    proxy_buffering off;
    proxy_request_buffering off;
    proxy_read_timeout 1h;
    proxy_send_timeout 1h;
    gzip off;
}
```

A node that cannot reach the API servers for 30 seconds or more fails the reads in progress, and
those jobs fail as they would on a lost network mount.

Check afterwards:

- [ ] Each transcode node shows as healthy on the nodes page and reports that it has a key.
- [ ] A transcode node without a key, or running with a key that was replaced, takes no new work:
  it stays listed, marked keyless or unhealthy, until it is issued a key or restarted with its
  current one.
- [ ] A transcode started on each node plays, seeks, and stops.
- [ ] On a node set to `core`, a transcode plays without a library mount, and
  `silo_node_source_bytes_sent_total` grows for that node.

[Transcode nodes](architecture/transcode-nodes.md) describes the design.

error code on the main API listener of any release without v1, except the retained probes. The
version-neutral node routes are not covered by that tombstone: each is retired or retained
individually, and a retired one does not answer `410`.

## Post-update verification

- [ ] `/api/v1/health` reports the server process healthy through the same origin used by operators.
- [ ] `/api/v1/ready` reports ready only after required dependencies are usable.
- [ ] The bundled web application loads without requesting `/api/v1`.
- [ ] A current native client can sign in, select a profile, browse, search, start playback, seek,
  report progress, stop playback, and sign out.
- [ ] A new download completes and its offline manifest, artwork, subtitles, integrity checks, and
  playback work.
- [ ] Every remote transcode node passes the checks under [Transcode nodes](#transcode-nodes).
- [ ] Every external webhook or callback receives a fresh test event.
- [ ] OAuth-backed integrations complete a new authorization flow.
- [ ] Installed plugin pages and static assets load without `/api/v1` requests.
- [ ] Previously sent tokenized links fail safely, and newly sent links work.
- [ ] Server diagnostics show the expected API major and contract digest.
- [ ] Logs and metrics contain no unexplained legacy-native traffic. Expected `/api/v1` attempts
  receive only the upgrade tombstone; separately retired version-neutral paths never execute old
  business behavior.

Both native clients call only `/api/v2` (apart from the retained health probe) and decode
it with handwritten models. The table lists each contract change the clients must handle and
where `silo-apple` (iOS, tvOS and macOS) and `silo-android` (phone and TV) stand on their main
branches. Validate both against the same server contract before release.

Treat unknown states as unavailable. Revisions reflect the runtime document and caller scope; do not parse them as numbers or use route presence as feature detection. | Done | Done for request and subtitle-provider status; pending for `getSubtitleAIStatus`, which decodes none of the three fields |
| Conditional capability reads | Store the document with its `ETag`, send `If-None-Match`, and reuse the matching body on bodyless `304`. Respect private cache directives. Partition caches by server, account, profile and relevant device/security context; revalidate after authority or configuration changes. | Pending | Pending |
| `getCatalogSearchCapabilities` | Allow `provider` to be absent when search is not configured. Use `state` before interpreting provider-specific limits or starting a search. | Done | Pending: `provider` is required and `state` is not checked |

## Recovery preparation

The preserved pre-1.0 artifact is the final pre-1.0 release itself — the version the deployment
ran immediately before 1.0 — not an arbitrary earlier alpha build. Keep that immutable image or
binary, its exact configuration, the matching client builds, and the verified pre-update database
backup until the 1.0 validation checklist passes. Silo does not guarantee that the final pre-1.0 release can read
a database migrated or written by 1.0. Unless the release notes explicitly certify that exact
combination, the recovery procedure is:

1. Stop every 1.0 API, proxy, and worker component.
2. Restore the complete pre-upgrade database and matching configuration, including the
   `/var/lib/silo/userdb` SQLite user store when `userdb.backend=sqlite` was in use.
3. Redeploy the preserved final pre-1.0 image or binary and its matching components.
4. Verify the restored deployment before allowing users or background work to resume.

This restore discards changes made after the backup. Do not attempt an in-place database downgrade
or restore selected v1 handlers. The final pre-1.0 release remains downloadable after validation as a
recovery artifact, but it is not a continuing supported API line and receives no new development.
